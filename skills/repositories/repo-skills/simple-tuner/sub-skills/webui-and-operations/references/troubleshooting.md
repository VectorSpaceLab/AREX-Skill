# Troubleshooting WebUI, API, Queue, Cloud, Workers, and Auth

Start with the smallest read-only probe that can explain the symptom. Do not retry destructive actions, approve jobs, rotate secrets, or stop training without explicit user confirmation.

## Server will not start

- **Port already in use**: choose another `--port` or stop the conflicting service.
- **Wrong bind address**: use a loopback address behind a proxy or a reachable interface for remote access.
- **SSL key/cert missing**: confirm both paths passed to `--ssl-key` and `--ssl-cert` exist from the server process perspective.
- **Self-signed TLS warning**: expected when `--ssl` auto-generates a certificate; use a trusted certificate or reverse proxy for production.
- **Missing SSL generation dependency**: install the cryptography dependency in the SimpleTuner environment before requesting autogenerated certs.
- **Autostart environment fails**: `--env <config-name>` validates the environment before launch. If validation fails, inspect the named config backend and environment layout before retrying.
- **Server dependency import error**: confirm the installed SimpleTuner variant includes WebUI/server dependencies such as FastAPI and uvicorn.
- **Kubeflow scheduling error**: all Kubeflow namespace/runtime/queue/worker-image/orchestrator arguments are required, and callback-only mode is not valid for scheduling.

## WebUI setup or login fails

- Query setup status first: `GET /api/cloud/auth/setup/status`.
- If setup is required, create the first admin before expecting normal login.
- If public registration is disabled, new users must be created by an admin.
- For API-key automation, verify the header is `X-API-Key` and that the key belongs to a user with the required permission.
- For cookie-based API calls, confirm the login request stored and reused the cookie jar.
- Check audit security events for repeated failed login attempts or expired sessions.

## API validation/start problems

- Validate before start: `POST /api/training/validate` should succeed before `POST /api/training/start`.
- If training/start accepts a minimal payload, remember it merges with the active environment. Confirm the intended environment is active.
- If using a one-off payload, include required model, output, dataloader, and step/epoch fields.
- Manual validation/checkpoint endpoints return an error when no training job is active.
- If stop/cancel fails, collect the active job ID from `GET /api/training/status` before retrying.
- If browser upload fails with a body-size error behind a proxy, raise the proxy request body limit for the upload route.

## Event stream or logs hang

- `GET /api/training/events?since_index=N` working while the stream hangs usually points to reverse-proxy buffering or timeout settings.
- Disable proxy buffering on stream routes and allow long read timeouts.
- Avoid proxies/CDNs that terminate long-lived event streams unless they explicitly support this use case.
- For job log following, confirm the job exists and that the server URL used by the CLI points to the same orchestrator that owns the job.

## Webhook delivery fails

- The callback URL must be reachable from the component sending the webhook. Internal-only addresses will not work for remote providers.
- Confirm firewall and reverse-proxy rules allow incoming callback requests.
- Use HTTPS for callbacks on untrusted networks.
- Validate that `webhook_config` is JSON serialized as a single form field when starting training through the API.
- If status events arrive but validation images/videos do not, confirm the training config actually enables validation previews or validation runs.
- If external validation/post-checkpoint/post-upload scripts fail, inspect the training logs and script exit behavior; SimpleTuner does not ingest arbitrary external script outputs for you.

## Queue stuck or misleading

- Check `GET /api/queue/stats` for `queue_depth`, `running`, `max_concurrent`, per-user/team limits, and local GPU state.
- If `running` equals the relevant concurrency limit, jobs are waiting for a slot.
- If jobs are `blocked`, inspect approval requests rather than manually resubmitting.
- If local jobs show running but allocated GPUs are empty, restart the server to trigger queue reconciliation and inspect GPU allocation errors in server logs.
- After bulk cancellation, pending jobs do not automatically start; call `POST /api/queue/process` or restart the server if scheduling should resume.
- Use `simpletuner jobs submit <config-name> --dry-run` to preview target, GPU availability, worker availability, queue position, and validation before resubmitting.

## Local GPU dispatch fails

- Confirm `num_processes` does not exceed available GPUs or local GPU concurrency limits.
- Check configured device IDs; use `--any-gpu` only when it is acceptable to ignore the config's preferred devices.
- Inspect `GET /api/system/status?include_allocation=true` for allocated/available devices and running local job IDs.
- If a job is rejected with `no_wait`, either free GPUs, lower requirements, or resubmit without `no_wait` so it can queue.

## Worker dispatch fails

- **Connection refused**: verify orchestrator URL, port, firewall, and server bind address.
- **Invalid token**: the worker token may have been rotated or copied with whitespace; create or rotate a token and restart the worker.
- **TLS verify error**: use a trusted certificate in production. Development-only no-verify modes should not be used for untrusted networks.
- **Worker offline**: check heartbeat timeout, network stability, GPU driver health, disk space, and worker process logs.
- **No idle workers**: jobs will queue until a matching worker becomes idle.
- **Label mismatch**: compare job `worker_labels` with worker labels. All requirements must match and glob patterns are supported.
- **GPU requirement mismatch**: reduce `num_processes` or add a worker with enough GPUs.
- **Draining worker**: a draining worker finishes current work and refuses new dispatch.

## Cloud job issues

- **Provider credentials missing/invalid**: configure credentials through the WebUI or cloud CLI secret prompt; do not paste real token values into handoffs.
- **Upload blocked**: review packaged dataset size and provider upload limits. Split or reduce the dataset before resubmission.
- **Unexpected spend approval**: inspect cost limit and approval rules; blocked jobs require explicit admin action.
- **Cloud job failed/cancelled**: cloud jobs are single-shot in this snapshot. Resubmission starts a new job; automatic checkpoint resume is not built in.
- **Need a multi-step pipeline**: orchestrate externally and chain API calls; the built-in cloud system does not model DAG dependencies.
- **Results not delivered back**: confirm the publishing destination, callback URL reachability, and any S3-compatible credentials or endpoint settings.

## External auth issues

- **OIDC invalid/expired state**: state expires after a short window; retry login and check time synchronization between SimpleTuner and the identity provider.
- **OIDC discovery unreachable**: verify outbound network access from the SimpleTuner server to the identity provider.
- **OIDC client mismatch**: re-check client ID/secret and allowed callback URL in the provider.
- **LDAP connection refused**: verify server URL, port, TLS mode, and firewall.
- **LDAP invalid credentials**: verify bind DN is a full DN, password is current, and the service account is not locked.
- **LDAP user or group not found**: inspect base DN, filters, username attribute, group filter, and whether group membership attributes match the directory schema.

## Audit-chain verification fails

- Treat audit verification failure as a security incident until explained.
- Export a read-only copy of affected audit rows for review through approved internal process.
- Do not attempt to edit audit rows through the database to repair the chain.
- Correlate with recent admin, credential, API key, and job approval events.
