# MiniMind Post-Training Data Formats

## Purpose

Read this before preparing or validating JSONL for MiniMind distillation-adjacent DPO, RLAIF, GRPO/CISPO, PPO, or Agentic RL. Use the bundled validator instead of launching a long run to discover schema errors.

```bash
python scripts/validate_post_training_jsonl.py \
  --input-file DATA.jsonl --schema auto --max-records 1000
```

If running from a different working directory, replace the script path with the path to this generated sub-skill's bundled script.

## Common JSONL and message rules

- JSONL means one complete JSON object per line; blank lines are ignored by the validator but should be removed for production data.
- Standard message roles are `system`, `user`, `assistant`, and `tool`.
- `content` should be a string. Use an empty string only when the field is truly a placeholder, such as an assistant message whose content will be generated online.
- `tools` belongs on the `system` message for MiniMind tool templates. It may be stored as a JSON array or as a string containing a JSON array.
- `tool_calls` belongs on an `assistant` message when supervised tool-call traces are being represented. It may be stored as a JSON array or as a string containing a JSON array.
- A MiniMind-native tool-call generated by the model is text in the form `<tool_call>{"name":"...","arguments":{...}}</tool_call>`; Agentic RL parses these tags from generated text.

## DPO / RLHF preference pair schema

Use this schema for static preference optimization. Each record must have `chosen` and `rejected`; both values are message arrays that represent the same prompt with different assistant continuations.

```jsonl
{"chosen":[{"role":"user","content":"Explain photosynthesis briefly."},{"role":"assistant","content":"Photosynthesis lets plants convert light, water, and carbon dioxide into sugars and oxygen."}],"rejected":[{"role":"user","content":"Explain photosynthesis briefly."},{"role":"assistant","content":"It is when animals breathe sunlight."}]}
```

Validation checklist:

- Both `chosen` and `rejected` are non-empty arrays of messages.
- Each side contains at least one assistant message that has non-empty `content` or valid `tool_calls`.
- The prompt side should match closely. The validator warns when the first user message differs.
- DPO evidence computes loss only over assistant response spans selected by a chat-template-derived assistant mask.
- Tool-specific DPO pairs are possible only if the active tokenizer/template supports the needed fields. Prefer plain message preference pairs unless the integrated skill has separately verified tool-aware DPO behavior.

Planning notes:

- DPO does not use `gt`, Reward Model, Critic, rollout engine, SGLang, or online generation.
- Use DPO for preference/safety/style alignment, not for tasks where correctness emerges only after tool execution or environment feedback.

## RLAIF prompt schema for PPO/GRPO/CISPO

Use this schema for single-turn online RLAIF. The trainer uses the messages before the final placeholder as the prompt and generates the assistant answer during rollout.

```jsonl
{"conversations":[{"role":"user","content":"Please explain what photosynthesis is."},{"role":"assistant","content":"无"}]}
```

Validation checklist:

- Top-level `conversations` is a non-empty message array.
- There is at least one `user` message.
- A final assistant placeholder is recommended. If the last assistant has substantive content, remember that PPO/GRPO-style online training does not learn that content as a supervised target.
- Do not include top-level `chosen`/`rejected`; that is DPO.
- Do not include top-level `gt` unless the route is Agentic RL or a separately designed verifier reward route.

Planning notes:

- `thinking_ratio` controls the probability that the prompt template opens explicit thinking for online generation.
- PPO defaults to one generation per prompt; GRPO/CISPO default to grouped generations.
- The default reward path uses a local external Reward Model plus length/format/repetition heuristics.

## Agentic RL messages/tools/gt schema

Use this schema when the model must perform multi-turn tool use and receive delayed trajectory reward. Each record must provide `conversations` and top-level `gt`. For tool-use objectives, include tools on the system message.

```jsonl
{"conversations":[{"role":"system","content":"Use tools when needed.","tools":"[{\"type\":\"function\",\"function\":{\"name\":\"calculate_math\",\"description\":\"Compute an arithmetic expression.\",\"parameters\":{\"type\":\"object\",\"properties\":{\"expression\":{\"type\":\"string\"}},\"required\":[\"expression\"]}}}]"},{"role":"user","content":"What is 256 * 37?"},{"role":"assistant","content":""}],"gt":["9472"]}
```

Validation checklist:

- Top-level `conversations` is an array with at least one user turn before the final placeholder.
- Top-level `gt` is a list. Use strings or numbers; avoid nested objects because reward matching expects scalar targets.
- The final conversation message is treated as a placeholder and excluded from the rollout prompt. Use an assistant placeholder for clarity.
- If the record is intended for tool-use training, a system message should include `tools` as an OpenAI-style function list.
- Every tool definition should have `type: "function"`, a function `name`, `parameters.type: "object"`, and `required` as a list.
- Tool names in generated `<tool_call>` text must match the provided tool list or they receive invalid-call penalties.

Planning notes:

- The evidence tool set for Agentic training includes `calculate_math`, `unit_converter`, `get_current_weather`, `get_current_time`, `get_exchange_rate`, and `translate_text` as deterministic mock tools. The final evaluation script evidence also includes `random_number` and `text_length` for tool-call evaluation cases.
- `gt` is matched against final answer text by string inclusion and numeric tolerance. Formatting can matter: include canonical numeric/string answers that should appear in the final response.
- Pure no-tool records can still be represented, but then `gt` may not produce the same signal as a tool-use trajectory. Prefer route-specific reward design for no-tool verifier tasks.

## Tool-call object shape

MiniMind-generated tool calls use compact JSON inside XML-like tags:

```text
<tool_call>{"name":"calculate_math","arguments":{"expression":"256 * 37"}}</tool_call>
```

OpenAI-style tool definitions use this shape:

```json
{
  "type": "function",
  "function": {
    "name": "calculate_math",
    "description": "Compute an arithmetic expression.",
    "parameters": {
      "type": "object",
      "properties": {
        "expression": {"type": "string"}
      },
      "required": ["expression"]
    }
  }
}
```

Common mistakes caught by the validator or smoke helper:

- `tools` is a Python repr string with single quotes rather than valid JSON.
- `tool_calls` contains malformed JSON or arguments that are a non-object string.
- Tool definition `required` is a string instead of a list.
- Agent RL `gt` is a scalar string or number instead of a list.
- The record has `gt` but no tools and no separate reward-plan explanation.
- A DPO record is accidentally passed to an RLAIF route or an RLAIF record to Agentic RL.

## Validator usage

Validate a file and auto-detect schema:

```bash
python scripts/validate_post_training_jsonl.py \
  --input-file DATA.jsonl --schema auto
```

Force Agentic validation and require tool definitions:

```bash
python scripts/validate_post_training_jsonl.py \
  --input-file AGENT_DATA.jsonl --schema agent-rl --require-tools
```

Treat warnings as failures before a long job:

```bash
python scripts/validate_post_training_jsonl.py \
  --input-file DATA.jsonl --schema auto --warnings-as-errors
```

Exit status:

- `0`: no errors; warnings may still be present unless `--warnings-as-errors` was used.
- `1`: schema errors, invalid JSON, or warnings promoted to errors.

## Route mismatch examples

| Symptom | Likely mismatch | Fix |
|---|---|---|
| File has `chosen`/`rejected` but user asks for PPO/GRPO | DPO data provided for online RLAIF | Route to DPO or convert to prompt-only RLAIF data with a reward plan. |
| File has `conversations` only but user asks for Agentic RL | Plain RLAIF data lacks `gt` and tool definitions | Add Agentic `gt` and system tools or route to PPO/GRPO. |
| File has `gt` as `"9472"` | Agent reward expects a list of targets | Use `"gt": ["9472"]`. |
| System `tools` is missing | Tool-use reward cannot validate generated names/arguments | Add OpenAI-style function definitions or treat the record as no-tool RLAIF. |
| Final Agent RL message is a user message | Placeholder trimming removes the wrong content | End with an assistant placeholder such as `{"role":"assistant","content":""}`. |
