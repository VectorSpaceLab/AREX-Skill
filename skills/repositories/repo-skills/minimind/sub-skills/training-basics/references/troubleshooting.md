# MiniMind training troubleshooting

Use this matrix when tokenizer validation, data loading, core training, LoRA, checkpoint resume, logging, or output discovery fails.

| Symptom | Likely cause | What to check | Recovery |
|---|---|---|---|
| `FileNotFoundError` or dataset path error at startup | Required JSONL file is missing or the command is being run from the wrong working directory | Confirm `--data_path` points to an existing JSONL file. Relative defaults such as `../dataset/sft_t2t_mini.jsonl` assume the training entrypoint directory. | Pass an explicit `--data_path`. Do not start full training until the validator can read the file. |
| JSON decode error or `datasets` fails reading JSON | Broken JSONL, multi-line JSON object, trailing comments, or invalid UTF-8 | Run `validate_minimind_jsonl.py` on the exact file. JSONL means one complete JSON object per line. | Rewrite fixtures as single-line JSON objects. Remove comments and blank invalid fragments. |
| `KeyError: 'text'` in pretraining dataset | Pretrain file is not in pretrain schema | Check each line has `{"text": "..."}` with a non-empty string. | Use `--schema pretrain` validator; route conversation files to SFT/LoRA instead. |
| SFT loads but loss is zero, `nan`, or labels appear all masked | Conversation lacks assistant spans or template tokens do not match expected assistant start/end markers | Check for assistant messages with non-empty `content` or valid `tool_calls`. Validate the tokenizer's BOS/EOS and chat template. | Add assistant targets. Use the MiniMind tokenizer or regenerate all weights/data consistently for a custom tokenizer. |
| Tool-call examples validate as JSON but training drops tool definitions | `tools` is not on a system message, or it is not a JSON-encoded string | Inspect the line with `--schema sft --strict`. | Put `tools` on the system message as a JSON string. Put `tool_calls` on assistant messages as a JSON string. |
| `json.loads` fails for `tools` or `tool_calls` | Field contains Python repr, single quotes, or already-expanded malformed JSON | Validate with `validate_minimind_jsonl.py`; check escaping of nested quotes. | Store nested objects as proper JSON strings, e.g. `"tool_calls":"[{\"name\":...}]"`. |
| Reasoning samples do not show expected thinking spans | `reasoning_content` absent, non-string, or mixed with content-level `<think>` unexpectedly | Check whether reasoning is in `reasoning_content` or inside `content`. | Prefer `reasoning_content` on assistant messages. Avoid relying on joint visible reasoning + tool call behavior without task-specific validation. |
| Token IDs differ from expected MiniMind IDs | Wrong tokenizer directory or custom tokenizer used with existing weights | Check `bos_token`, `eos_token`, `pad_token`, vocabulary size, and chat template with the validator. | Use the tokenizer that matches the weights. Treat a new tokenizer as a new model family. |
| `OSError` or load error for `pretrain_*.pth` / `full_sft_*.pth` | `--from_weight` expects a missing file in the output directory | Match `--from_weight`, `--hidden_size`, `--use_moe`, and `--save_dir` to the actual weight. | For SFT, create/download/provide pretrain weights or intentionally set `--from_weight none`. For LoRA, provide full-SFT weights or choose the correct prefix. |
| Dense/MoE suffix mismatch | Weight was trained with different `--use_moe` | Dense weights are `prefix_{hidden_size}.pth`; MoE weights are `prefix_{hidden_size}_moe.pth`. | Rerun with the matching `--use_moe` value. Do not load dense and MoE states as interchangeable. |
| Shape mismatch on load | Different `hidden_size`, layer count, vocab size, MoE setting, or tokenizer/model mismatch | Compare model knobs and tokenizer vocab size used to create the weight. | Recreate the config to match the weight, or train a new compatible weight. `strict=false` loading does not make incompatible checkpoints semantically valid. |
| LoRA run says compile disabled | Native LoRA monkey-patches linear `forward` methods | `train_lora.py` turns `--use_compile 1` back to `0`. | Keep `--use_compile 0` for LoRA. Use compile only for dense pretrain/SFT experiments. |
| LoRA output has only a small state dict | Expected behavior: LoRA saves only `.lora.` tensors | Check output name `{lora_name}_{hidden_size}{_moe}.pth`. | For serving/export, merge LoRA with the base model through the inference/export route owned by `inference-serving`. |
| LoRA quality regresses base behavior badly | Domain data too narrow, high LR, too many epochs, or base weight mismatch | Confirm `--from_weight` matches the base model intended for LoRA. Inspect domain/general mix. | Lower LR/epochs, mix general SFT data, or use full SFT with a carefully balanced dataset if LoRA capacity is insufficient. |
| `torch.cuda.is_available()` is false | CUDA runtime, driver, or PyTorch build mismatch | Check PyTorch backend availability before selecting device. | Use `--device cpu` only for tiny validation or very small LoRA experiments. Install a compatible CUDA PyTorch build before real GPU training. |
| CUDA OOM | Batch/sequence/model too large, MoE overhead, or too many workers/pinned buffers | Check `--batch_size`, `--max_seq_len`, `--hidden_size`, `--num_hidden_layers`, `--use_moe`, and world size. | Reduce batch size or sequence length, increase `--accumulation_steps`, use BF16, disable compile during debugging, or use more GPU memory. |
| BF16/FP16 numerical issues | Hardware does not support chosen dtype well, or LR too high | Compare `--dtype bfloat16` vs `float16`; check for `nan` loss. | Use BF16 on supported CUDA devices. Try lower LR, smaller batch, or FP32 for tiny CPU checks. |
| DDP hangs at startup | `torchrun` environment incomplete, wrong backend for device, or one worker crashed | Confirm launch uses `torchrun --nproc_per_node <N>` and all processes see CUDA. | Reproduce single-process first. Then retry DDP with fewer workers and no online logging. |
| Resume finds no checkpoint | `--from_resume 1` is looking for a different prefix, hidden size, MoE suffix, or checkpoint directory | Check expected resume name `{prefix}_{hidden_size}{_moe}_resume.pth`. For LoRA, prefix is `--lora_name`. | Reuse the same stage flags or copy/rename only when you are certain the checkpoint corresponds to the run. |
| Resume skips too many or too few batches after changing GPU count | MiniMind rescales saved step by saved/current world size | Logs should mention GPU-count change and adjusted step. | Accept approximate progress for recovery, or resume with the original GPU count when exact batch order matters. |
| Resume fails loading optimizer/scaler | Optimizer parameter set changed, LoRA/dense switch changed, or compile/wrapper changed state names | Compare dense vs LoRA, model shape, and DDP/compile settings. | Resume with matching settings. If only model weights are needed, start a new run from the model output weight instead of the resume checkpoint. |
| SwanLab/WandB login or network error | Online logging requested without credentials or network | `--use_wandb` enables `swanlab as wandb`. | Rerun without `--use_wandb` for offline training. If resuming with logging, ensure credentials and project are available. |
| Output weight not found after training | Wrong `--save_dir`, save interval not reached before failure, or only checkpoint directory inspected | Training saves stage outputs to `--save_dir` and resume checkpoints to the checkpoint directory. Saves also occur at epoch end. | Inspect both output and checkpoint directories. Use explicit `--save_dir` and stage prefix. Ensure the main process reached a save point. |
| Temporary `.tmp` checkpoint remains | Save interrupted during atomic replacement | Check for complete `.pth` beside `.tmp`. | Prefer the complete `.pth`. If only `.tmp` exists, treat the save as interrupted and resume from the previous complete checkpoint or rerun the last segment. |
| `datasets`, `transformers`, or tokenizer imports fail | Environment missing training dependencies | Requirements include `datasets`, `transformers`, `jinja2`, `swanlab`, and other training/runtime packages; Torch is backend-specific and commented out in requirements. | Install a backend-compatible environment. Remember FastAPI/Uvicorn are API-serving needs, not core training requirements. |
| `num_workers` data-loader errors on constrained hosts | Too many worker processes or platform-specific multiprocessing issue | Default `--num_workers` is `8`. | Reduce to `--num_workers 0` or a small number for debugging and tiny fixtures. |

## Minimal triage sequence

1. Run JSONL validation on a tiny sample or the first bounded number of lines.
2. Run tokenizer validation if a tokenizer directory is involved.
3. Run `tiny_training_smoke.py` on CPU to prove imports and random-tensor training plumbing.
4. If CUDA is required, run the same tiny smoke on `cuda:0` before full training.
5. Start the full route with small `--save_interval`, no online logging, and no compile for the first debug pass.
6. After the route is stable, re-enable DDP, logging, compile, or larger batch/sequence settings one change at a time.
