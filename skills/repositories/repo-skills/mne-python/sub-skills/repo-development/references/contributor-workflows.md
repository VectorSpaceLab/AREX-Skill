# Contributor workflows for MNE-Python maintenance

Use this reference for repository-editing tasks. It distills source evidence from `AGENTS.md`, `CONTRIBUTING.md`, `pyproject.toml`, `Makefile`, contributor-guide excerpts, maintainer helpers, and installed API signatures. Source paths are provenance, not runtime dependencies.

## AI-assisted contribution policy

- MNE-Python contributions require human judgment, contextual understanding, domain knowledge, and familiarity with project goals.
- Do not submit issues or pull requests generated by fully automated tools.
- Any AI-assisted code or documentation must be personally reviewed, understood, and tested by the human contributor before submission under their name.
- Do not paste AI-generated text into issue descriptions, PR descriptions, or comments. Provide technical notes that the human can rewrite.
- If AI tools assisted, the PR description must disclose the tools used and the manner/scope of assistance.
- Pay special attention to AI-assisted specialized algorithms: copied or closely paraphrased code can create license violations.
- Do not adapt outside code unless the source license is BSD-compatible: BSD, MIT, ISC, Apache-2.0, or public domain are acceptable examples. GPL/LGPL/AGPL, non-commercial, no-derivatives, or unknown licenses are not acceptable. Attribute adapted code directly above the adapted block.

## Start-of-task checklist

1. Identify the target area: implementation, public API, docs, tests, changelog, deprecation, optional dependency, or maintainer tooling.
2. Confirm whether the request is repository maintenance. If the user is analyzing data or using MNE as a library, route to the analysis sub-skills.
3. Check that `import mne` resolves to the checkout being edited. Use the bundled helper:

   ```bash
   python skills/disco/mne-python/sub-skills/repo-development/scripts/check_mne_checkout.py --repo-root .
   ```

4. Keep the patch small. Avoid unrelated formatting or import rewrites.
5. Before finalizing, choose focused checks from the command matrix below. Escalate to broader tests only when the edited area requires it.

## Environment and install commands

MNE-Python is a pure-Python package using hatchling/hatch-vcs for versioning; there is no separate compile/build step beyond installing the package and optional dependencies.

Typical editable development setup:

```bash
python -m pip install -e ".[test_extra,doc]"
pre-commit install --install-hooks
```

If using `uv`, install from the dependency groups defined by the project configuration rather than inventing ad-hoc dependency sets. Minimum Python support in the inspected configuration is Python 3.11.

Useful import sanity probes:

```bash
python -c "import mne; print(mne.__version__); print(mne.__file__)"
python skills/disco/mne-python/sub-skills/repo-development/scripts/check_mne_checkout.py --repo-root .
```

## Focused command matrix

Run the smallest check that exercises the change. The full suite is slow.

| Change type | Suggested local checks |
| --- | --- |
| Any Python code style/docstring-adjacent change | `make ruff` |
| Single function/class bug fix | `pytest path/to/test_file.py::test_name --verbose` |
| Test-file iteration by keyword | `pytest path/to/test_file.py -k keyword --verbose` |
| Broad module change | `pytest path/to/package_or_test_dir --verbose` |
| Full non-ultraslow suite when truly needed | `pytest -m "not ultraslowtest" mne` |
| Public API or docstring changes | `pytest mne/tests/test_docstring_parameters.py` |
| Import-time or optional-dependency boundary changes | `make nesting` |
| Documentation text/API-page changes | `make ruff` plus a docs build target below |
| Doctest-sensitive doc changes | `make test-doc` |
| Example/tutorial affected by a regex-selectable file | `PATTERN=<regex> make -C doc html-pattern` |
| Formatting/linking docs without executing examples/tutorials | `make -C doc html-noplot` |
| Dataset-dependent tests | Fetch only the needed data with the dataset helper commands below |

Useful pytest flags during debugging: `-x` to stop on first failure, `--pdb` for post-failure debugging, and `--durations=5` to spot slow tests.

## Dataset and optional dependency practices

- Prefer the `testing` dataset over larger sample datasets when adding tests. It contains small versions of most MNE object families.
- Fetch datasets explicitly only when a selected test needs them:

  ```bash
  python -c "import mne; mne.datasets.testing.data_path(verbose=True)"
  python -c "import mne; mne.datasets.sample.data_path(verbose=True)"
  ```

- Missing optional dependencies often appear as pytest skips or import errors in a narrow area. Install the dependency that matches the edited feature rather than adding it globally.
- Optional/heavy dependencies such as Matplotlib, SciPy, scikit-learn, pandas, PyVista, and Qt should be imported lazily inside the function or method that needs them, unless the file already has a justified local pattern.
- For no-network or no-testing-data diagnostics, the project Makefile exposes guarded targets that set skip environment variables.

## Code and API edit checklist

- Classes use `CamelCase`; functions and variables use `snake_case`. Prefer clear names such as `n_samples` over abbreviations such as `nsamples`.
- No bare `*args` or `**kwargs` in public signatures unless an existing API pattern requires it.
- Avoid nested functions/methods for new code; prefer private module-level helpers.
- Methods usually mutate in place and return `self`; module-level functions should return copies when applicable.
- Preserve file-local import style. Source guidance includes both AI-agent-specific advice favoring absolute imports for new code and contributor-guide advice favoring relative imports in core code but absolute imports in tests/tutorials. When editing existing files, match local style and ask before broad changes.
- Add or update tests with new functionality. Keep tests compact, prefer existing test files, and avoid long or data-heavy cases unless necessary.
- For visualization API changes, expose a public function in `mne.viz` and have object methods call the function, not the reverse. Visualization functions take `show`; default colormap is `RdBu_r` for signed/zero-centered data and `Reds` otherwise.

## Deprecation workflow

Public API changes should be avoided when possible. When a user-visible API must change:

1. Use the `mne.utils.deprecated` decorator for deprecated functions/classes.
2. Use `mne.utils.warn(..., FutureWarning)` for deprecated parameters.
3. Add tests that assert the warning is emitted with `pytest.warns(FutureWarning, match=...)`.
4. Search internal call sites and update them immediately. Do not wait until the end of the deprecation cycle.
5. Add an `apichange` changelog fragment if behavior changes require a deprecation cycle.

## Changelog fragments and contributor names

User-facing changes generally need a towncrier fragment:

```text
doc/changes/dev/<PR-number>.<type>.rst
```

Allowed types in the inspected configuration: `notable`, `dependency`, `bugfix`, `apichange`, `newfeature`, and `other`.

Guidelines:

- Skip changelog only for very minor documentation typo fixes or when a maintainer explicitly labels the PR as not needing one.
- Do not edit generated aggregate changelog files directly.
- Use public API roles such as `:func:`, `:class:`, and `:meth:` in changelog text when naming public endpoints.
- New contributors are credited with `:newcontrib:`; existing contributors use a normal reST name reference.
- Every credited name needs a matching target in `doc/changes/names.inc`. Missing or duplicate/conflicting targets cause changelog or docs failures.
- If the PR number is unknown, ask the human maintainer whether to wait, use the eventual PR number, or stage a clearly marked placeholder that must not be submitted unchanged.

## Final handoff checklist for a maintenance answer

- State the exact files changed and why.
- State which public API, docs, tests, changelog, and names updates are required or intentionally not required.
- State which commands were run and which were skipped, with reasons.
- Surface AI-policy responsibilities: human review, testing, disclosure, and no unreviewed generated PR/issue text.
- Surface any optional dependency, data, docs-build, or environment limits that remain.
