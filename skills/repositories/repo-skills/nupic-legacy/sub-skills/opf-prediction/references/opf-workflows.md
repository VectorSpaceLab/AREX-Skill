# OPF Workflows

This reference is the operational recipe for NuPIC legacy Online Prediction Framework (OPF) model runs, experiment directories, prediction extraction, and checkpoints. Evidence was distilled from the legacy OPF quick start, OPF guide, bundled OPF examples, experiment runner, OPF source modules, and OPF tests; do not reopen or run those original files to use this skill.

## Preconditions

- Use a NuPIC legacy runtime: Python 2.7-era `nupic`, compiled `nupic.bindings`, `numpy` 1.12.x-era compatibility, and `pycapnp`/capnproto for capnp serialization paths. Installation failures belong in root [`../../../references/troubleshooting.md`](../../../references/troubleshooting.md).
- Validate CSV/model-param structure in [`../../data-and-configuration/`](../../data-and-configuration/) before debugging OPF behavior. OPF only works reliably when field names and declared types agree across CSV headers, encoders, and inference settings.
- Use [`../../htm-algorithms/`](../../htm-algorithms/) when a failure is really about encoder width, SP/TM parameters, classifier settings, anomaly likelihood, or direct algorithm state.
- Use [`../../swarming/`](../../swarming/) when a `model_params.py`, `description.py`, or model config was generated by hypersearch/swarming; return here to run the selected OPF model.

## Workflow 1: run an OPF model over a typed CSV stream

Inputs you need:

- A NuPIC model config loaded as a Python `dict`. YAML examples usually have top-level keys `model`, `version`, `aggregationInfo`, and `modelParams`.
- A NuPIC CSV with three header rows: names, types, and flags. See [`../../data-and-configuration/`](../../data-and-configuration/) for exact CSV semantics.
- The predicted field name, e.g. `consumption`. It must match the CSV name row and the encoder/model-param field name.
- A small record limit for smoke testing before a full run.

Steps:

1. Load the model params with YAML or JSON.
2. Create the model:

   ```python
   from nupic.frameworks.opf.model_factory import ModelFactory
   model = ModelFactory.create(modelConfig, logLevel=40)
   ```

3. Enable inference with the exact predicted field:

   ```python
   model.enableInference({'predictedField': 'consumption'})
   ```

4. Convert every input value before `model.run`. Do not pass raw CSV strings for numeric or datetime fields.

   ```python
   import datetime

   record = {
       'timestamp': datetime.datetime.strptime('7/2/10 0:00', '%m/%d/%y %H:%M'),
       'consumption': float('21.2'),
   }
   result = model.run(record)
   ```

5. Extract predictions from `result.inferences` only after checking that the key and step exist. Multi-step models often emit empty or `None` predictions during warm-up.

   ```python
   best = result.inferences.get('multiStepBestPredictions', {})
   all_predictions = result.inferences.get('multiStepPredictions', {})

   for step in (1, 5):
       value = best.get(step)
       if value is None:
           continue
       confidence = all_predictions.get(step, {}).get(value)
       print(step, value, confidence)
   ```

6. For a bounded check using your own files, run the bundled smoke helper:

   ```bash
   python scripts/opf_prediction_smoke.py --params model.yaml --csv data.csv --predicted-field consumption --limit 5
   ```

Validation checks:

- `modelConfig['model']` is usually `HTMPrediction` for OPF HTM prediction.
- `modelConfig['modelParams']['inferenceType']` matches the requested task, commonly `TemporalMultiStep` for multi-step prediction.
- `modelConfig['modelParams']['sensorParams']['encoders']` has an encoder for each model input field used by OPF.
- `modelConfig['modelParams']['clParams']['steps']` contains the requested prediction horizons, often as a comma-separated string such as `'1,5'`.
- The record passed to `model.run` contains the predicted field under the exact same name used in `enableInference`.

## Workflow 2: inspect one-step and multi-step predictions

Relevant result shape:

```python
result.predictionNumber       # 0-based record index
result.rawInput               # original typed record dict
result.sensorInput            # translated/encoded sensor payload when populated
result.inferences             # dict of inference outputs
result.metrics                # metric outputs when OPF task driver computed metrics
result.predictedFieldName     # predicted field recorded by the model
```

For multi-step prediction:

```python
best = result.inferences['multiStepBestPredictions']
all_predictions = result.inferences['multiStepPredictions']

one_step_value = best[1]
one_step_confidence = all_predictions[1][one_step_value]
five_step_value = best[5]
five_step_confidence = all_predictions[5][five_step_value]
```

Notes:

- Step keys are integers (`1`, `5`), not strings, in the classic examples and tests.
- `multiStepBestPredictions[step]` is the best value. `multiStepPredictions[step]` maps candidate predicted values to probabilities/confidences.
- During early learning, a step may be absent or its best prediction may be `None`. Treat this as warm-up unless it persists after enough records.
- Anomaly workflows may instead use `anomalyScore` and `anomalyLabel` keys; classification workflows may use `classification` and `classConfidences`.

## Workflow 3: run an OPF experiment directory

An OPF experiment directory is a directory containing `description.py`. The installed experiment runner consumes that directory and optional runner flags. Use the bundled help wrapper first:

```bash
python scripts/opf_experiment_help.py --summary
python scripts/opf_experiment_help.py --check-import
python scripts/opf_experiment_help.py --runner-help
```

Canonical installed-runner command form:

```bash
python -m nupic.frameworks.opf.experiment_runner [options] EXPERIMENT_DIR
```

Common actions:

```bash
# List task labels from description.py.
python -m nupic.frameworks.opf.experiment_runner --listTasks EXPERIMENT_DIR

# Run all tasks with tiny testing iteration counts when the experiment supports it.
python -m nupic.frameworks.opf.experiment_runner --testMode EXPERIMENT_DIR

# Run selected tasks. Use a standalone dot so --tasks does not consume EXPERIMENT_DIR.
python -m nupic.frameworks.opf.experiment_runner --tasks LearnTask InferTask . EXPERIMENT_DIR

# Create a checkpoint named Initial without running tasks.
python -m nupic.frameworks.opf.experiment_runner -c Initial EXPERIMENT_DIR

# List checkpoints created under the experiment directory.
python -m nupic.frameworks.opf.experiment_runner --listCheckpoints EXPERIMENT_DIR

# Load a checkpoint and run tasks.
python -m nupic.frameworks.opf.experiment_runner --load Initial EXPERIMENT_DIR

# Run without writing checkpoint directories after each task.
python -m nupic.frameworks.opf.experiment_runner --noCheckpoint EXPERIMENT_DIR
```

Experiment runner rules:

- `-c`, `--listCheckpoints`, `--listTasks`, and `--load` are mutually exclusive.
- `-c` and `--noCheckpoint` are mutually exclusive.
- Exactly one experiment directory is required.
- `--tasks` accepts one or more task labels and stops at a standalone dot (`.`) or next option. Put `.` before `EXPERIMENT_DIR` to avoid the directory being consumed as a task label.
- Local stream sources in generated experiments often need a `file://` URI; validate source paths with [`../../data-and-configuration/`](../../data-and-configuration/).

## Workflow 4: checkpoint and load models

Direct API checkpointing:

```python
from nupic.frameworks.opf.model_factory import ModelFactory

model = ModelFactory.create(modelConfig, logLevel=40)
model.enableInference({'predictedField': 'consumption'})
# ... run records ...
model.save('/path/to/my_saved_model_dir')
loaded = ModelFactory.loadFromCheckpoint('/path/to/my_saved_model_dir')
```

Directory shape for direct legacy pickle serialization:

```text
my_saved_model_dir/
  model.pkl
  modelextradata/       # optional, model-specific
```

Capnproto/new serialization path:

```python
model.writeToCheckpoint('/path/to/my_capnp_checkpoint')
loaded = ModelFactory.loadFromCheckpoint('/path/to/my_capnp_checkpoint', newSerialization=True)
```

Directory shape for capnp serialization:

```text
my_capnp_checkpoint/
  model.data
```

Experiment-runner checkpoints:

```text
EXPERIMENT_DIR/
  savedmodels/
    <checkpoint-label>.nta/
      model.pkl             # or model.data with --newSerialization
      modelextradata/       # optional
```

Recovery checks:

- If `ModelFactory.loadFromCheckpoint` fails, confirm you passed the model directory itself, not its parent.
- For experiment runner `--load`, pass the checkpoint label only, not `<label>.nta` and not a filesystem path.
- Do not point `model.save` at an arbitrary non-model directory. The legacy implementation refuses to delete a directory unless it already looks like a saved model.

## Workflow 5: metrics and prediction logs

When OPF task driver or an experiment computes metrics, `result.metrics` and output logs use labels that encode inference element, metric, steps, window, and field. Example labels include:

```text
multiStepBestPredictions:multiStep:errorMetric='aae':steps=1:window=200:field=consumption
multiStepBestPredictions:multiStep:errorMetric='avg_err':steps=5:window=200:field=consumption
```

Use metrics to compare runs, but debug raw `result.inferences` first. If the metric is missing while predictions exist, inspect the experiment task control and metric specs rather than rebuilding the model.
