# Cross-Cutting Troubleshooting

## When to read

Read this when a Langchain-Chatchat task fails before it clearly belongs to one sub-skill. For CLI/config failures, continue to `server-setup-and-cli`; for request/route/vector-store failures, continue to `knowledge-base-and-api`; for SDK/import/adapter failures, continue to `python-sdk-and-adapters`.

## Install and import failures

| Symptom | Likely cause | Recovery |
| --- | --- | --- |
| `chatchat: command not found` | `langchain-chatchat` is not installed in the active Python environment, or console scripts are not on `PATH` | Run `python -m pip show langchain-chatchat`; run `python -m chatchat.cli --help` if the script path is unavailable; reinstall in a Python 3.10/3.11 environment. |
| `ModuleNotFoundError: No module named 'chatchat'` | Wrong environment or failed package install | Verify `python -c "import sys; print(sys.executable)"`; install `langchain-chatchat`; avoid Python 3.13 for this package version. |
| `ModuleNotFoundError: No module named 'open_chatchat'` | The SDK import package is spelled `open_chatcaht` in this repository | Use `import open_chatcaht`; document the spelling in user code and verify with `from open_chatcaht.chatchat_api import ChatChat`. |
| `ModuleNotFoundError: No module named 'xinference_client'` with model auto-detect warnings | Optional Xinference client extra is not installed in the Chatchat environment | Only install `langchain-chatchat[xinference]` if the user wants Chatchat to inspect Xinference models from the same env; otherwise configure explicit model names/endpoints and keep provider env separate. |
| Warnings from `pydantic_settings` about `json_file` | Current settings classes include config keys not backed by a JSON settings source | Usually non-fatal; focus on generated YAML files and pydantic validation errors that block startup. |

## `CHATCHAT_ROOT` and configuration problems

| Symptom | Likely cause | Recovery |
| --- | --- | --- |
| Config files appear in an unexpected directory | `CHATCHAT_ROOT` was unset, so Chatchat used the current working directory | Pick a persistent data root, export `CHATCHAT_ROOT`, rerun `chatchat init`, and audit with `sub-skills/server-setup-and-cli/scripts/chatchat_config_audit.py`. |
| Startup uses stale model names after package upgrade | YAML templates were generated by an older package version | Backup existing YAML/data, run `chatchat init` again to refresh templates, then reapply user-specific provider settings. |
| SQLite/knowledge-base DB errors during imports or startup | The data root directories or DB tables were not initialized | Run `chatchat init` without `--recreate-kb` first; run `chatchat kb --create-tables` if only tables are missing. |
| `chatchat init --recreate-kb` fails | It rebuilds vectors and needs a reachable embedding model | First run plain `chatchat init`, configure provider and embedding model, validate provider reachability, then run `chatchat kb -r`. |

## Provider and model failures

| Symptom | Likely cause | Recovery |
| --- | --- | --- |
| Logs say the default LLM or embedding model is not found | Configured `DEFAULT_LLM_MODEL` or `DEFAULT_EMBEDDING_MODEL` does not match provider model names | Inspect `model_settings.yaml`; use provider UI/API to list loaded model names; set `MODEL_PLATFORMS` and default model fields consistently. |
| Chat/RAG request returns model-not-found or connection errors | Chatchat API is up but provider endpoint is down, wrong, unauthenticated, or not OpenAI-compatible | Verify provider independently; test `/v1/models` only after provider is configured; check `api_base_url`, `api_key`, proxy, and model names. |
| Provider install conflicts with Chatchat dependencies | Installing model-serving frameworks and Chatchat in one env can create incompatible dependencies | Use separate envs or Docker services for provider and Chatchat; connect through OpenAI-compatible HTTP endpoints. |
| Docker/Xinference deployment starts but Chatchat gives no answers | Containers are running, but models are not loaded/registered in provider | Use provider UI/API to load both LLM and embedding models before using Chatchat WebUI/API. |

## Knowledge-base and vector-store failures

| Symptom | Likely cause | Recovery |
| --- | --- | --- |
| `chatchat kb -r` hangs or fails on embeddings | Embedding model endpoint is unreachable or model name is wrong | Fix provider config first; lower concurrency only after connectivity is proven. |
| FAISS works but Milvus/Postgres/Elasticsearch fails | External vector DB service config is incomplete | Check `kb_settings.yaml` service host/port/credentials and test the DB outside Chatchat; do not call FAISS success proof of external DB readiness. |
| Uploaded docs do not appear in retrieval | Files were uploaded without vector-store refresh, wrong KB name, or score threshold/top_k hides results | Use KB list/search routes; confirm `to_vector_store`, `chunk_size`, `chunk_overlap`, `score_threshold`, and `top_k`. |

## API and SDK failures

| Symptom | Likely cause | Recovery |
| --- | --- | --- |
| SDK connection refused | Chatchat API server is not running or SDK `base_url` points to the wrong host/port | Start `chatchat start --api`; verify API docs in browser or with a simple GET to `/`; set `base_url` or `CHATCHAT_API_BASE`. |
| Streaming parser sees SSE `data:` chunks instead of plain JSON | Some routes stream OpenAI-compatible chunks or agent step events | Use the SDK streaming generator or an SSE-aware parser; for retrieval-only checks, use `return_direct=True` where supported. |
| Tool calls do nothing or error | Tool name is disabled/misconfigured or model does not support agent/tool behavior | Fetch `/tools` first; check tool config; use `tool_choice` with `extra_body.tool_input` for manual tool input when model agent behavior is weak. |

## When to stop and ask for external setup

Stop and ask for explicit user approval before:

- Downloading or serving LLM/embedding models.
- Starting Docker Compose or modifying system Docker/NVIDIA runtime.
- Running AutoDL scripts or scripts that kill processes, write hard-coded paths, or download models.
- Rebuilding large knowledge bases or deleting/pruning user KB files.
- Installing provider-specific GPU packages into an existing user environment.
