# CLI, XML lifecycle, and execution

## Input lifecycle

OpenMC consumes XML input generated by the Python API or written by the user.
The standard separate-file lifecycle is:

1. Build a trusted `Model` (or the individual materials, geometry, settings,
   tallies, and plots objects).
2. Export into a dedicated directory with `model.export_to_xml(directory=...)`,
   or export one `model.xml` with `model.export_to_model_xml(path=...)`.
3. Confirm the required model inputs are present before launching native code.
   Separate-file runs require `materials.xml`, `geometry.xml`, and
   `settings.xml`; `tallies.xml` and `plots.xml` are optional. A single
   `model.xml` contains the model sections in one file.
4. Configure cross sections through the materials/settings data reference or
   `OPENMC_CROSS_SECTIONS`, then validate the index and referenced HDF5 paths.
5. Run from a controlled working/output directory and retain the stdout/stderr
   and generated files.

The Python API's `Model.export_to_xml` creates its target directory when needed.
`Model.export_to_model_xml` accepts an XML file path or a directory (where it
writes `model.xml`). `Geometry.export_to_xml(path='geometry.xml',
remove_surfs=False)` is a lower-level geometry-only export; it is not a complete
simulation input by itself. Do not substitute geometry creation or tally/data
semantics for this runtime route; hand those topics to their owning skills.

OpenMC's native executable searches the current directory when invoked without
an input path. It can also receive a directory or a single XML input path. If a
path is supplied, output still goes to the current working directory unless the
model's output settings choose another path. Make the distinction explicit when
copying or locating `statepoint.*.h5`, `summary.h5`, `tallies.out`, plot images,
tracks, or restart files.

## Direct command-line execution

Basic commands:

```sh
cd /path/to/run-directory
openmc
openmc /path/to/run-directory
openmc /path/to/run-directory/model.xml
openmc --version
openmc --help
```

Useful flags exposed by the executable are:

| Flag | Effect |
|---|---|
| `-n N`, `--particles N` | Use `N` particles per generation/batch |
| `-s N`, `--threads N` | Use `N` OpenMP threads |
| `-e`, `--event` | Use event-based parallelism |
| `-g`, `--geometry-debug` | Check for cell overlaps during particle moves; use fewer particles because it can be expensive |
| `-p`, `--plot` | Run plotting mode |
| `-c`, `--volume` | Run stochastic volume-calculation mode |
| `-r FILE`, `--restart FILE` | Restart from a statepoint or particle-restart file |
| `-t`, `--track` | Write particle tracks, bounded by the configured maximum |
| `-q V`, `--verbosity V` | Set output verbosity |
| `-v`, `--version` | Print the native version |
| `-h`, `--help` | Print command help |

Treat `-g` as a diagnostic run, not a production performance setting. Use
`-n` to bound a smoke test, but do not treat a low-particle run as a meaningful
scientific result.

## Python executor and `Model.run`

For a directory of already-exported XML files:

```python
import openmc

openmc.run(
    particles=100,
    threads=2,
    cwd='run-directory',
    path_input='run-directory',
    output=True,
)
```

`openmc.run` launches the executable through a subprocess. `openmc_exec` can be
an explicit executable path, and `mpi_args` is a list such as
`['mpiexec', '-n', '4']`. A nonzero executable status is raised as a
`RuntimeError`; preserve the native output when diagnosing it.

For a complete Python model, `Model.run` is the higher-level orchestration:

```python
model.export_to_model_xml('run-directory/model.xml')
last_statepoint = model.run(
    particles=100,
    threads=2,
    cwd='run-directory',
    openmc_exec='openmc',
    export_model_xml=True,
)
```

When the C API is not initialized, `Model.run` exports XML and uses the command
line. If the model has been initialized through `Model.init_lib`, execution
uses `openmc.lib` instead; options such as threads, geometry-debug, restart,
and tracks must be set during initialization, not passed later to `Model.run`.
`Model.run` returns the newest statepoint path when one is produced. Keep
statepoint files closed before launching another run; an open HDF5 handle can
prevent `summary.h5` from being rewritten.

Use a context manager for result files:

```python
with openmc.StatePoint('statepoint.10.h5') as statepoint:
    keff = statepoint.keff
```

Detailed result and tally interpretation belongs to the tallies/results route.

## OpenMP and MPI choices

- **OpenMP:** It must be enabled at CMake configure time (`OPENMC_USE_OPENMP`;
  default `ON`). Choose the number of runtime threads with `-s`, the `threads`
  argument, or `OMP_NUM_THREADS`. Do not oversubscribe a constrained job.
- **MPI:** It must be enabled at CMake configure time (`OPENMC_USE_MPI=ON`) and
  requires a compatible MPI compiler/runtime. Launch the executable through the
  local MPI wrapper, for example:

  ```sh
  mpiexec -n 4 openmc /path/to/run-directory
  ```

  The Python equivalent is `mpi_args=['mpiexec', '-n', '4']`. The exact binding
  and launcher options are implementation/cluster-specific. Never claim MPI
  support from the presence of `mpi4py` alone: check the native CMake configure,
  the launcher, and the actual run.
- **Hybrid jobs:** On multi-node systems, select MPI processes per node and
  OpenMP threads within each process according to the scheduler and hardware.
  Avoid multiplying process count by thread count beyond allocated CPUs.
- **Reproducibility:** Native strict-FP builds and a fixed thread count help
  test comparability. Threaded tally reductions can differ because floating
  point addition is non-associative; exact or bit-level agreement should not be
  promised across arbitrary thread/compiler/MPI choices.

## Bounded test selection

Use the least expensive check that answers the question:

1. Package/API smoke: import OpenMC, construct a tiny object, and export XML
   without transport.
2. Setup tests: use the selected model/executor unit tests only when pytest and
   the package are installed. These can validate XML and command construction,
   but subprocess/transport sections need the executable and data.
3. Native C++ checks: after a successful CMake build, run `ctest --output-on-failure`
   or a deliberately selected CTest subset. Configure with
   `-DOPENMC_ENABLE_STRICT_FP=ON` for reference-oriented testing.
4. Regression/transport/depletion: run only with the required cross-section,
   ENDF, NJOY, MPI, and other prerequisites explicitly present. Full suites are
   not a default smoke test.

For the project's broad test suite, use `python -m pip install -e .[test]`, a
fully installed/importable Python package, an executable on `PATH`, the required
cross-section library, and (where applicable) `OPENMC_ENDF_DATA` and `njoy`.
The project recommends `OMP_NUM_THREADS=2` when floating-point test stability
matters. Record skipped data-dependent and optional-integration tests instead
of converting them into passes.
