# Evaluation Workflows

## Minimal CLI run

```bash
rllm eval <benchmark> --agent <agent-name-or-module:object> --model <model-name>
```

If no `--base-url` is supplied, rLLM uses configured provider/model state from `rllm model setup`. If `--base-url` is supplied, also pass `--model` because OpenAI-compatible clients still require a model string.

Useful options:

- `--evaluator`: host-side evaluator registry name or `module:class`, overriding per-task verifier resolution.
- `--split`: dataset split.
- `--concurrency`: parallel request count.
- `--attempts`: independent rollouts per task; reports pass@k for k up to attempts.
- `--max-examples` and `--task-indices`: bounded development runs.
- `--sandbox-backend`, `--sandbox-concurrency`, `--snapshot/--no-snapshot`, `--warm-queue-size`: sandbox provisioning controls.
- `--output`, `--save-episodes/--no-save-episodes`, `--episodes-dir`: result persistence.
- `--sampling-params` or shortcuts `--temperature`, `--top-p`, `--max-tokens`: sampling overrides passed through the gateway/provider.
- `--ui/--no-ui`: live UI logging if logged in.

## Programmatic pattern

1. Implement or load an `AgentFlow`.
2. Implement or load an `Evaluator` unless the dataset/task metadata resolves one.
3. Load tasks from the dataset/benchmark layer.
4. Run through rLLM evaluation runner/engine so gateway trace enrichment, sandbox hooks, and result collection remain consistent with CLI behavior.

Use direct calls to a custom `AgentFlow` only for protocol tests. For real benchmark runs, prefer `rllm eval` or the packaged runner APIs so per-task verifier and sandbox resolution run in the same way as the CLI.

## Harness selection

Built-in harness names are catalog-backed. Common signal names in this revision include ReAct-style agents, bash/sandboxed agents, Claude Code/Mini SWE Agent variants, and oracle/helper harnesses. Use `rllm agent list` for the installed environment; use `rllm agent register` for custom project scaffolds generated by `rllm init`.

## Result interpretation

Evaluation writes aggregate JSON and, by default, per-episode JSON files. Saved episodes contain the task metadata, trajectories, steps, rewards, and correctness metadata that later SFT/data curation can consume. `rllm view` is the local UI entry for browsing saved episodes; see `../../cli-ops/SKILL.md` for CLI operation details.

## Sandboxed eval

A rollout may need a sandbox because:

- the flow declares `needs_env = True` or accepts keyword-only `env`;
- the verifier kind is sandbox-side;
- the task/dataset layout declares an environment.

For sandboxed tasks, keep `--sandbox-backend` explicit during debugging and use `--no-snapshot` to separate snapshot cache issues from verifier/agent logic.
