# Superduper Component Workflow Patterns

Use these patterns to assemble components into working AI application graphs. The examples are intentionally small, deterministic, and local-first.

## Pattern 1: Apply a Callable Model Directly

For early debugging, call the model before involving a database.

```python
from superduper import ObjectModel

def normalize(text: str) -> str:
    return " ".join(str(text).split()).lower()

model = ObjectModel(identifier="normalize", object=normalize, datatype="str")
assert model.predict(" Hello   WORLD ") == "hello world"
assert model.predict_batches(["A", "B"]) == ["a", "b"]
```

Use this before building a listener. If `predict` fails locally, a listener will fail after doing more work.

## Pattern 2: Register a Single Listener

A listener reads data from a query, maps fields into a model, and writes outputs.

```python
from superduper import Listener, ObjectModel, Table

# Source table first.
db.apply(Table(identifier="documents", fields={"id": "str", "text": "str"}))
db["documents"].insert([
    {"id": "d1", "text": "Hello world"},
    {"id": "d2", "text": "Second document"},
])

def token_count(text: str) -> int:
    return len(str(text).split())

count_model = ObjectModel(identifier="token-count", object=token_count, datatype="int")
count_listener = Listener(
    identifier="count-text",
    model=count_model,
    select=db["documents"].select(),
    key="text",
)
db.apply(count_listener)

# Read outputs from the listener-managed table/field.
rows = db[count_listener.outputs].select().execute()
```

Operational notes:

- Apply the source `Table` before applying the listener.
- `db.apply(listener)` persists the model, listener, managed output table, and apply jobs unless `jobs=False` is passed.
- `jobs=False` is useful for registration or export-only workflows but will not populate listener outputs.
- If `db.cfg.force_apply` or `force=True` is used, an existing component version may be replaced; otherwise content changes are versioned according to component hashes.

## Pattern 3: Chain Listeners

Use `listener.outputs` as the downstream field and declare the upstream listener dependency.

```python
from superduper import Listener, ObjectModel

def add_suffix(value: str) -> str:
    return f"{value}->a"

def add_second(value: str) -> str:
    return f"{value}->b"

model_a = ObjectModel(identifier="a", object=add_suffix, datatype="str")
model_b = ObjectModel(identifier="b", object=add_second, datatype="str")

listener_a = Listener(
    identifier="a",
    model=model_a,
    select=db["documents"].select(),
    key="text",
)
db.apply(listener_a)

listener_b = Listener(
    identifier="b",
    model=model_b,
    select=db[listener_a.outputs].select(),
    key=listener_a.outputs,
    upstream=[listener_a],
)
db.apply(listener_b)
```

When building longer chains:

- Apply upstream listeners first, or group the components in an `Application` with explicit `upstream` links.
- Use the upstream listener's output table in the downstream `select`.
- Use the upstream listener's output field as the downstream `key`.
- If a query API asks for output ids rather than field names, pass `listener.predict_id` and then read the result through `listener.outputs`.

## Pattern 4: Join Multiple Upstream Outputs

For a model with multiple positional inputs, `key` is a tuple/list of field names. Include upstream outputs in the selected query.

```python
from superduper import Document, Listener, ObjectModel

def combine(title, body, score):
    return Document({"title": title, "body": body, "score": score}).unpack()

combine_model = ObjectModel(
    identifier="combine-fields",
    object=combine,
    datatype="json",
)

combine_listener = Listener(
    identifier="combine",
    model=combine_model,
    select=db["documents"].select("id", "title", "body").outputs(score_listener.predict_id),
    key=("title", "body", score_listener.outputs),
    upstream=[score_listener],
)
db.apply(combine_listener)
```

This pattern is useful for feature graphs: one listener creates a feature, a second listener consumes both original fields and that feature.

## Pattern 5: Use Application as a Workflow Bundle

`Application` is a component that groups related components.

```python
from superduper import Application

pipeline = Application(
    identifier="document-enrichment",
    components=[documents_table, listener_a, listener_b, combine_listener],
)
db.apply(pipeline)
```

Application guidance:

- Include source tables or schemas when the application should be self-contained.
- Keep outputs generated by listeners out of the hand-authored component list unless you have a specific reason to manage them directly.
- Preserve `upstream` links on listeners and custom components so dependency order is explicit.
- Use applications as the object to export/share when the workflow is more important than a single component.

## Pattern 6: Training and Validation Scaffold

Training is represented as components: a model has a `trainer`, and validation is described by `Validation`, `Dataset`, and `Metric` components.

```python
from superduper import Dataset, Metric, ObjectModel, Trainer, Validation

class ToyTrainer(Trainer):
    def fit(self, model, db, train_dataset, valid_dataset):
        # Replace this with the actual fit logic. Keep side effects explicit.
        model.metric_values.setdefault("seen_train_rows", []).append(len(train_dataset))
        return model

def predict_label(features):
    return int(sum(features) > 0)

def accuracy(predictions, targets):
    return sum(p == t for p, t in zip(predictions, targets)) / max(1, len(targets))

valid_dataset = Dataset(identifier="valid-docs", select=db["documents"].select())
validation = Validation(
    identifier="basic-validation",
    key=("features", "label"),
    datasets=[valid_dataset],
    metrics=[Metric(identifier="accuracy", object=accuracy)],
)

model = ObjectModel(
    identifier="toy-classifier",
    object=predict_label,
    datatype="int",
    trainer=ToyTrainer(identifier="toy-trainer", key="features", select=db["documents"].select()),
    validation=validation,
)
db.apply(model)
```

Checklist:

- Ensure the trainer `key` matches the model signature.
- If relying on automatic train/valid split behavior, include a `_fold` field with values `train` and `valid` in the selected table.
- Keep heavyweight training, downloads, and credentials outside smoke examples.
- Put metrics in `Validation` when they should run after fitting or on apply.

## Pattern 7: Simplified RAG Component Shape

A lightweight retrieval-augmented generation layout can be expressed without requiring a notebook, model download, or provider credentials. Keep vector indexing and provider install details in their own routes.

```python
from superduper import Listener, Model, ObjectModel

class Chunker(Model):
    chunk_size: int = 200

    def predict(self, text):
        words = str(text).split()
        return [" ".join(words[i : i + self.chunk_size]) for i in range(0, len(words), self.chunk_size)]

class PromptingRAG(Model):
    prompt_template: str
    select: object
    key: str
    llm: Model

    def _build_prompt(self, query, docs):
        chunks = [doc[self.key] for doc in docs]
        context = "\n\n".join(chunks)
        return self.prompt_template.format(context=context, query=query)

    def predict(self, query: str):
        select = self.select.set_variables(db=self.db, query=query)
        docs = [row.unpack() for row in select.execute()]
        return self.llm.predict(self._build_prompt(query, docs))

def echo_llm(prompt: str) -> str:
    return prompt[:200]

chunker = Chunker(identifier="chunker", datatype="json")
chunk_listener = Listener(
    identifier="chunk-documents",
    model=chunker,
    select=db["documents"].select(),
    key="text",
    flatten=True,
)

llm = ObjectModel(identifier="local-echo-llm", object=echo_llm, datatype="str")
rag = PromptingRAG(
    identifier="simple-rag",
    prompt_template="Context:\n{context}\n\nQuestion: {query}\nAnswer:",
    select=db[chunk_listener.outputs].select(),
    key=chunk_listener.outputs,
    llm=llm,
    upstream=[chunk_listener, llm],
)
```

This pattern captures the component architecture:

- `Chunker` splits a source field into chunks.
- A `Listener(flatten=True)` stores one output record per chunk.
- A RAG model stores a query template, a retrieval `select`, an input key, and an LLM-like model.
- A local `ObjectModel` can stand in for the LLM during deterministic tests.

Do not use this route for nearest-neighbor scoring, vector-index maintenance, provider API calls, or Streamlit/server deployment details.

## Pattern 8: Streamlit and Scheduled Components

Streamlit and cron components are workflow components, but they require a server/runtime to execute.

```python
from superduper import FunctionCronJob, Streamlit

def refresh(db):
    # deterministic maintenance logic
    return None

refresh_job = FunctionCronJob(function=refresh, schedule="0 0 * * *")

def demo(db, title="Demo"):
    import streamlit as st
    st.title(title)

streamlit_page = Streamlit(identifier="demo", demo_func=demo, demo_kwargs={"title": "Demo"})
```

Treat cron/server execution as deployment-dependent. Constructing these components locally is safe; running them requires the relevant service.
