# Data and configuration reference

Use this reference when validating DeepKE supervised inputs, editing Hydra YAMLs, or preparing prediction checkpoint/model paths. The sibling `data-preparation` sub-skill owns conversion from annotation exports; this reference owns the formats that supervised training/prediction expects after conversion.

## Global layout conventions

DeepKE's classic examples are organized around a task/scenario directory with:

- `conf/` YAML files for Hydra configuration.
- `data/` or `data/origin/` split files and label inventories.
- `run.py` or task-specific training entrypoints.
- `predict.py` for prediction when the scenario supports it.
- `checkpoints/`, `log/`, `logs/`, `output/`, or model-specific save paths generated by training.

The actual working directory matters because many YAML defaults are relative. When running a native DeepKE entrypoint, run it from the task/scenario directory that owns its `conf/` folder unless you have audited every path override.

## Hydra and YAML caveats

- Several configs contain `cwd: ???`; this is intentionally populated at runtime. Do not try to read it as a finished value outside Hydra.
- Defaults select model and train/predict fragments, for example `model: lm` or `hydra/model: lstmcrf`. Changing the model often requires updating a second model-specific YAML.
- Path fields may be interpreted relative to the scenario working directory, not the caller's current shell. For prediction checkpoints, prefer a fully resolved path or run from the scenario directory and record the relative base.
- Some documented commands use Hydra overrides such as `+train=few_shot` or `hydra/run=single_transfer.yaml`; keep the override attached to the command, not just the YAML edit.
- If using Weights & Biases, set the config's `use_wandb`/`wandb` field intentionally. Leave it false for offline smoke checks.
- Multi-GPU flags differ by scenario (`use_multi_gpu`, `gpu_ids`, `gpus`, or `device`). Treat them as scenario-specific; do not copy blindly between NER, RE, AE, EE, and few-shot configs.

## Standard NER data

### BIO text format

Standard NER uses one token or character plus one BIO label per line. Blank lines separate sentences.

```text
本 O
报 O
北 B-LOC
京 I-LOC
9 O
月 O
4 O
日 O

秦 B-PER
始 I-PER
皇 I-PER
兵 O
马 O
俑 O
位 O
于 O
陕 B-LOC
西 I-LOC
省 I-LOC
```

Expected split files:

| File | Purpose |
| --- | --- |
| `train.txt` | Training split. |
| `valid.txt` | Validation/dev split. |
| `test.txt` | Test split. |

Validation expectations:

- Each nonblank row has exactly two logical fields: token and label.
- Labels are `O` or `B-<TYPE>`/`I-<TYPE>`.
- Every `<TYPE>` appears in the training YAML `labels` list without the BIO prefix.
- Blank lines delimit sentences; missing blank lines can create very long sequences.
- For English prediction, set `lan: en` and ensure NLTK tokenization resources are installed or available.

### JSON and DOCX inputs

The standard NER docs also accept `json` and `docx` as preparation inputs, but the training path consumes converted `txt`. Use the sibling `data-preparation` conversion helper before training and inspect the rendered BIO file.

## Standard NER config knobs

| Field | Meaning | Typical action |
| --- | --- | --- |
| `hydra/model` | Selects `bert` or `lstmcrf` in the standard NER config. | Match the intended model family and checkpoint/vocab. |
| `lan` | Prediction language, commonly `zh` or `en`. | Set `en` before English prediction. |
| `labels` | Entity type inventory without BIO prefix. | Match `train.txt` and cnSchema/custom labels. |
| `learning_rate` | Optimizer learning rate. | BERT often needs a lower value than BiLSTM-CRF. |
| `num_train_epochs` | Training epochs. | Increase for stable BERT fine-tuning; reduce for smoke checks. |
| `output_dir` | Checkpoint output directory. | Confirm it is writable and separate from data. |
| `use_gpu`, `gpu_id`, `use_multi_gpu` | GPU selection. | Use CPU only for small import/config checks; training normally benefits from GPU. |
| `model_vocab_path` in BiLSTM-CRF model YAML | Vocabulary pickle used by BiLSTM-CRF prediction. | Ensure it is generated from the training data and reused for prediction. |

## W2NER data/config notes

W2NER is under the standard NER family but has its own config and entrypoints. It supports unified NER, including flat, nested, and discontinuous entities. Use the same split concept (`train.txt`, `valid.txt`, `test.txt`) but audit W2NER-specific fields such as model YAML, GPU `device`, tokenizer language handling, and output/checkpoint paths.

## Few-shot NER data/config

Common files:

| Dataset family | Expected files |
| --- | --- |
| CoNLL-2003 | `train.txt`, `valid.txt`, `test.txt`, `indomain-train.txt`. |
| MIT Movie / MIT Restaurant / ATIS | `k-shot-train.txt` where `k` may be 10, 20, 50, 100, 200, or 500, plus `test.txt`. |

Important config fields:

| Field | Meaning |
| --- | --- |
| `bart_name` | BART checkpoint name or local path. Chinese few-shot requires a Chinese BART-compatible asset. |
| `dataset_name` | Dataset switch used by the loader. |
| `device` | Usually `cuda`; CPU is normally too slow for meaningful training. |
| `save_path` | Where the tuned model/prompt is saved. |
| `load_path` | Existing checkpoint/prompt to resume or predict from. Prediction requires a non-empty value. |
| `write_path` | Prediction output path. |
| `use_prompt`, `prompt_len`, `prompt_dim`, `freeze_plm`, `learn_weights` | Prompt-tuning behavior. |

Validation expectations:

- The dataset name must match an actual data subfolder or loader branch.
- k-shot split names must match the config's `data_dir`/dataset assumptions.
- If `load_path` is null during prediction, prediction cannot load a trained model.

## Cross-domain NER data/config

Cross-domain CP-NER-style workflows use JSON and schema files per domain.

| File | Purpose |
| --- | --- |
| `train.json` | Domain training data. |
| `val.json` | Validation data. |
| `test.json` | Test data. |
| `record.schema` | Schema used by the generative record/spot-asoc decoder. |
| `entity.schema`, `event.schema`, `relation.schema` | Additional schema files present in the domain layout. |

Key config fields:

| Field | Meaning |
| --- | --- |
| `model_name_or_path` | T5/generative PLM or tuned model path. |
| `model_ckpt_path` | Existing checkpoint path for prefix/label-word saving or transfer. |
| `source_prefix_path` | Single source-domain prefix/model path. |
| `target_prefix_path` | Target domain prefix/model path. |
| `multi_source_path` | Comma-separated source prefix paths for multi-source transfer. |
| `record_schema` | Relative or absolute path to the target domain schema. |
| `output_dir`, `logging_dir` | Where tuned models and logs are written. |
| `decoding_format` | Usually `spotasoc`; changing it changes output interpretation. |

Validation expectations:

- Do not mix source-domain schema with target-domain data.
- Every comma-separated path in `multi_source_path` must exist and be readable.
- `output_dir` should not overwrite a source prefix unless intentionally refreshing it.

## Multimodal NER data/config

Text follows a CoNLL-like format and includes an image id marker such as:

```text
IMGID:213820
RT O
@user O
Driving I-ORG
test O
Leicester B-ORG
```

Expected companion assets:

| Asset | Purpose |
| --- | --- |
| Original images | Raw visual input. |
| RCNN detected object folder | Local object features. |
| Visual grounding object folder | Grounded visual features. |
| Text split files | Token/label input. |

Key fields:

| Field | Meaning |
| --- | --- |
| `bert_name` | Text encoder checkpoint/name/path. |
| `vit_name` | CLIP/Vision Transformer checkpoint/name/path. Use a local path when offline. |
| `dataset_name` | Dataset selector, e.g. Twitter-style variants. |
| `max_seq` | Maximum token sequence length. |
| `aux_size`, `rcnn_size` | Visual feature sizes. |
| `save_path`, `load_path` | Checkpoint save/load path. |

Validation expectations:

- Each image id in the text split must resolve to the expected image/object records.
- `vit_name` should point to a CLIP-compatible model; some older dependency sets cannot load it remotely.

## Standard RE data

Standard RE uses sentence-level relation classification with one row per `(sentence, head, tail)` candidate.

Required CSV columns:

| Column | Meaning | Validation |
| --- | --- | --- |
| `sentence` | Raw sentence containing the entity pair. | Non-empty string. |
| `relation` | Gold relation label. | Must appear in the relation inventory. |
| `head` | Head entity text. | Should be a substring of `sentence`. |
| `head_offset` | Start offset of head. | Should point to `head`. |
| `tail` | Tail entity text. | Should be a substring of `sentence`. |
| `tail_offset` | Start offset of tail. | Should point to `tail`. |

Example row shape:

```csv
sentence,relation,head,head_offset,tail,tail_offset
孔正锡，导演，2005年以一部温馨的爱情电影《长腿叔叔》敲开电影界大门,导演,长腿叔叔,23,孔正锡,0
```

`relation.csv` maps relation labels to ids and may include entity type columns. If a relation can connect multiple entity type pairs, DeepKE guidance allows prefixing or including entity types in the relation input, but the model/data contract must be consistent.

Supported preparation inputs include `csv`, `json`, and `xlsx`; convert non-CSV inputs before training.

## Standard RE config knobs

| Field | Meaning |
| --- | --- |
| `model` default | Selects `cnn`, `rnn`, `transformer`, `capsule`, `gcn`, or `lm`. |
| `lm_file` | Pretrained LM name or local path for the `lm` model. |
| `num_relations` | Number of relation labels/classes. cnSchema RE uses 51 in the documented quick-load setup. |
| `epoch`, `batch_size`, `learning_rate` | Main training hyperparameters. |
| `use_gpu`, `gpu_id`, `use_multi_gpu`, `gpu_ids` | Accelerator selection. |
| `predict.fp` | Checkpoint path for prediction. Prediction cannot work with the placeholder value. |
| `plot_utils`, `show_plot`, `predict_plot` | Visualization options; disable for headless automation unless needed. |

## Few-shot RE data/config

Few-shot RE commonly uses JSON-lines/text objects with tokenized sentence and entity spans:

```json
{"token": ["the", "most", "common", "audits", "were", "about", "waste", "."], "h": {"name": "audits", "pos": [3, 4]}, "t": {"name": "waste", "pos": [6, 7]}, "relation": "Message-Topic(e1,e2)"}
```

Expected files:

| File | Purpose |
| --- | --- |
| `rel2id.json` | Relation labels / answer words to ids. |
| `train.txt` | Training split. |
| `val.txt` | Validation split. |
| `test.txt` | Test split. |

Key config fields include `data_dir`, `model_name_or_path`, `model_class`, `litmodel_class`, `save_path`, `load_path`, `train_from_saved_model`, `batch_size`, `max_seq_length`, `ptune_k`, `use_prompt`, and PyTorch Lightning accelerator settings (`gpus`, `devices`, `precision`).

## Document-level RE data/config

Document-level RE expects DocRED-style JSON.

| File | Purpose |
| --- | --- |
| `train_annotated.json` | Manually annotated training data. |
| `train_distant.json` | Distantly supervised training data. |
| `dev.json` | Validation split. |
| `test.json` | Test split. |
| `rel2id.json` | Relation id mapping. |
| `rel_info.json` | Relation metadata. |

Important fields:

| Field | Meaning |
| --- | --- |
| `train_file`, `dev_file`, `test_file` | Which JSON split files to read. |
| `num_class` | Relation class count; must match the mapping. |
| `max_seq_length` | Maximum document token length. |
| `model_name_or_path`, `transformer_type` | Encoder model and type. |
| `train_from_saved_model`, `load_path`, `save_path` | Resume/load/save behavior. |
| `train_batch_size`, `test_batch_size`, `gradient_accumulation_steps` | Memory-sensitive batch behavior. |

## Multimodal RE data/config

Expected MNRE-style assets:

| Asset | Purpose |
| --- | --- |
| `txt` or text split folder | Text/entity/relation instances. |
| `ours_rel2id.json` or equivalent | Relation label mapping. |
| Original image folder | Raw images. |
| RCNN detected object folder | Detected object features. |
| Visual grounding folder and metadata | Grounded visual object features. |

Fields mirror multimodal NER: `bert_name`, `vit_name`, `max_seq`, `aux_size`, `rcnn_size`, `save_path`, `load_path`, `device`, `batch_size`, and training epochs.

## Standard AE data/config

AE follows the standard RE model/config family but the label inventory is attributes rather than relations.

Expected split files:

| File | Purpose |
| --- | --- |
| `train.csv` | Training split. |
| `valid.csv` | Validation split. |
| `test.csv` | Test split. |
| `attribute.csv` | Attribute type/id mapping. |

Common columns:

| Column | Meaning |
| --- | --- |
| `sentence` | Raw sentence. |
| `attribute` or `att` | Attribute label. |
| `ent` / `entity` | Entity text. |
| `ent_offset` / `entity_offset` | Entity start offset. |
| `val` / `value` | Attribute value text. |
| `val_offset` / `value_offset` | Value start offset. |

Key config differences from RE:

- `num_attributes` replaces `num_relations` in the embedding config.
- `attribute.csv` replaces `relation.csv`.
- `predict.fp` is still the checkpoint path.

## Standard EE data/config

EE is a two-stage pipeline over event triggers and arguments.

### Dataset choices

| Dataset | Expected preparation |
| --- | --- |
| `DuEE` | Use the extracted DuEE folder layout. |
| `ACE` | Prepare raw `dev.json`, `test.json`, `train.json`, then preprocess into `trigger`, `role`, and `schema` folders. |

Important training fields:

| Field | Meaning |
| --- | --- |
| `data_name` | `ACE` or `DuEE`. |
| `model_name_or_path` | BERT-like model path/name; English model for ACE, Chinese model for DuEE. |
| `task_name` | `trigger` for event detection/trigger classification, `role` for event argument extraction. |
| `do_train`, `do_eval`, `do_predict` | Stage actions. |
| `max_seq_length`, `per_gpu_train_batch_size`, `per_gpu_eval_batch_size` | Sequence/batch settings. |
| `data_dir`, `tag_path`, `output_dir` | Parsed by runtime code from dataset/task settings. |
| `dev_trigger_pred_file`, `test_trigger_pred_file` | Trigger-stage prediction JSON used by role pipeline prediction. |

Prediction fields:

| Field | Meaning |
| --- | --- |
| `do_pipeline_predict` | Whether role prediction uses predicted trigger files. |
| `model_name_or_path` | Trained role model path for role prediction. |
| `dev_trigger_pred_file`, `test_trigger_pred_file` | Must point to trigger-stage outputs. |

DEGREE variant note: DEGREE has a separate preprocessing/train/predict path and may require different dependency versions. Treat it as resource- and config-dependent; verify dependencies before running.

## cnSchema quick-load data/config

cnSchema is an off-the-shelf Chinese NER/RE use case.

| Component | Expectation |
| --- | --- |
| NER model | Downloaded model directory with transformer/tokenizer files or a supported NER checkpoint layout. |
| RE model | Downloaded `.pth` checkpoint for standard RE LM-style prediction. |
| Entity inventory | 28 cnSchema entity types in the documented release. |
| Relation inventory | 50 named cnSchema relation types plus an other/no-relation class in the documented RE setup. |
| NER config | Set prediction text, choose the model family, and point the model YAML at the checkpoint/model assets. |
| RE config | Set `predict.fp`, `num_relations: 51`, and an LM model path/name. |

Quick-load limitations:

- cnSchema extracts only the supported schema. For a custom schema, train NER/RE on custom data instead.
- Joint NER+RE over all detected entity pairs can produce false candidate pairs when a sentence contains many entities.
- If a downloaded model lacks tokenizer/config files, it is not a complete transformer model directory for NER.
