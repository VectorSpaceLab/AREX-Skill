# Compatibility and version boundaries

These compatibility statements are taken from the repository's README and
compile-time branches. They are historical operating guidance, not a promise
that an untested current release will accept the code or deserialize an old
engine.

## Repository-stated TensorRT matrix

| Demo/path | Repository guidance | Practical interpretation |
|---|---|---|
| GoogLeNet and MTCNN | TensorRT 3.x+ | Caffe parser and native code contain branches for old APIs; validate the exact target, especially parser/library names. |
| SSD (outside this sub-skill) | TensorRT 5.x+ | Not a dependency of the legacy Caffe workflows. |
| YOLO (outside this sub-skill) | TensorRT 6.x+ | Not evidence for these Caffe demos. |
| INT8 | TensorRT 6.x+, CUDA compute ≥6.1 | Not required for GoogLeNet/MTCNN FP16/FP32 engine creation. |
| DLA | TensorRT 7.x+, Xavier NX tested | Not used by these Caffe workflows. |
| MODNet | TensorRT 7.x+ | Not evidence for Caffe parser compatibility. |

The README gives a concrete example of TensorRT 5.1.6 on JetPack 4.2.2 for
GoogLeNet and MTCNN screenshots. Treat that as historical evidence only.

## What the source actually supports

The C++ builders explicitly branch on `NV_TENSORRT_MAJOR`:

- TensorRT 3-era code uses `createNetwork`, `buildCudaEngine`, old `DimsCHW`,
  and `setHalf2Mode`.
- TensorRT 4–5 use `Dims3` and `setFp16Mode` where available.
- TensorRT 6 changes `IHostMemory` method qualifiers and retains the legacy
  builder route.
- TensorRT 7 uses `createNetworkV2(0)`, a builder config, 64 MiB workspace,
  and `buildEngineWithConfig`.
- `trtNet.h` adds `noexcept` to logger/memory methods only at TensorRT 8+.

This is a source-compatibility intent, not a complete TensorRT 8/9/10 port.
The wrappers still call deprecated binding APIs such as `getBindingIndex`,
`getBindingDimensions`, `bindingIsInput`, `enqueue`, and `destroy`. A modern
runtime may compile with compatibility headers, fail compilation, fail to link
against removed parser libraries, or reject an engine generated by another
major release.

## Selection procedure

1. Identify the target JetPack or installed TensorRT major version and CPU
   architecture (`aarch64` Jetson versus `x86_64`). Do not start with a
   prebuilt engine from another version.
2. Confirm that `NvCaffeParser.h` and the parser library are installed. Modern
   TensorRT distributions may omit or separate Caffe parser support.
3. Build and deserialize engines on that same target. Preserve the builder's
   binding verification output.
4. Compile `pytrt` against the same headers and libraries used by the engine
   builder. The checked-in `setup.py` has hard-coded x86 TensorRT 7.1.3.4
   include/library paths and CUDA defaults; adapt paths only for the selected
   environment.
5. Run `--help` only after importing `pytrt` succeeds, then run a local image
   trial. A help-only pass does not prove engine inference.
6. Record any source edits as a compatibility patch. Do not call an edited
   port equivalent to the repository snapshot without a separate comparison.

## Architecture and engine constraints

- `common/Makefile.config` chooses `TARGET=aarch64` or `TARGET=x86_64` and
  changes CUDA library paths/compiler behavior accordingly. Set it explicitly
  when auto-detection is not the target you intend.
- Serialized engines contain target/runtime assumptions. Rebuild when moving
  between Jetson and x86_64, GPU generations, or materially different
  TensorRT/CUDA versions.
- MTCNN's fixed PNet `(3,710,384)` stack and maximum nine scales are model/code
  contracts, not arbitrary input-size settings. Keep the frame resize policy.
- TensorRT's `platformHasFastFp16()` selects FP16 in the builders; otherwise
  they build FP32. Do not compare accuracy or timing across precision modes
  without recording which branch was selected.

## Known historical caveats

- The MTCNN weights/descriptors use ReLU/Scale/Eltwise replacements because
  TensorRT 3.x/4.x did not support PReLU in the original model. Replacing them
  with an unrelated MTCNN release changes the graph contract.
- `pytrt.pyx` selects a stage initializer by substring (`det1`, `det2`, or
  `det3`) in the engine path. Rename paths only if this behavior is preserved
  or the wrapper is patched and retested.
- The asynchronous GoogLeNet script has an uninitialized `show_help` local in
  its keyboard handler; use synchronous inference for baseline validation or
  patch and test the async variant.
- No claim is made here for Windows, CPU-only inference, non-CUDA TensorRT, or
  current TensorRT API modernization.
