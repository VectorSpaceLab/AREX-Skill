# Repository maintenance troubleshooting

Use this reference when a Flower maintainer command fails or a repository change
looks correct locally but CI reports generated-code, migration, docs, or public
API problems.

## Stale generated protobufs

**Typical symptoms**

- A proto-related check reports `Changes detected` after regeneration.
- CI fails after a `.proto` edit because generated Python or type-stub files are
  missing from the diff.
- A contributor edited `framework/py/flwr/proto/*_pb2*.py` directly.

**Likely cause**

The source of truth is `framework/proto/flwr/proto/*.proto`; generated outputs
under `framework/py/flwr/proto/` must match generated results from those sources.
The proto parity check reruns generation and compares generated files to `HEAD`.

**Recovery**

```bash
cd framework
uv run --no-sync --python=3.11.14 ./dev/protoc.sh
uv run --no-sync --python=3.11.14 ./dev/check-protos.sh
```

Then inspect the diff. Commit regenerated `*_pb2.py`, `*_pb2.pyi`,
`*_pb2_grpc.py`, and `*_pb2_grpc.pyi` outputs when they changed because the
`.proto` source changed. If only generated files changed and no `.proto` changed,
revert the generated edits. Add serialization/deserialization coverage for
wire-format changes, commonly near `framework/py/flwr/common/serde_test.py` or a
module-specific test.

**Caution**

`check-protos.sh` can fail in a dirty local tree because it intentionally checks
whether regenerated files differ from `HEAD`. Use it as a clean-tree or CI-parity
check, not as proof that an uncommitted generated diff is wrong.

## Alembic migration drift

**Typical symptoms**

- `./dev/check-migrations.sh` fails after changing table metadata.
- A hand-written revision does not match SQLAlchemy metadata.
- A generated revision extends the wrong branch head or has an unexpected
  `down_revision`.
- SQLite tests fail around schema alteration or timestamp behavior.

**Likely cause**

The schema metadata under `framework/py/flwr/supercore/state/schema/` changed
without a matching generated revision under
`framework/py/flwr/supercore/state/alembic/versions/`, or the revision was
manually written without matching the repository's Alembic branch rules.

**Recovery**

Use the generator-first workflow from `framework/`:

```bash
uv run --no-sync --python=3.11.14 python -m dev.generate_migration "Describe schema change"
uv run --no-sync --python=3.11.14 ./dev/check-migrations.sh
```

Review the generated migration before committing:

- `down_revision` and selected branch head should match the intended branch
  (`flwr@head` by default).
- Autogenerated operations should match the metadata diff; remove accidental
  changes and add explicit data migration logic for renames/removals.
- SQLite-compatible operations should use Alembic patterns such as
  `batch_alter_table` when needed.
- If table metadata changed, update the schema documentation. The framework
  format script regenerates `framework/py/flwr/supercore/state/schema/README.md`
  through `paracelsus`.

If a manual Alembic experiment created a local `state.db`, remove it before
rerunning generator or check commands.

## Docs build prerequisites and generated docs

**Typical symptoms**

- Sphinx starts but fails because `pandoc` is missing.
- `make html` succeeds in one shell but not through the repo script because the
  wrong uv project/environment is active.
- Docs checks fail after generated API docs were not refreshed.
- `docs/build/` or generated distribution artifacts appear in a PR diff.

**Likely cause**

Framework docs require both Python dev dependencies and the system `pandoc`
executable. Framework and Flower Datasets docs use different package projects
and scripts.

**Recovery**

Framework docs:

```bash
cd framework
uv sync --locked --python=3.11.14 --all-extras --all-groups
uv run --no-sync --python=3.11.14 ./dev/build-docs.sh
```

Flower Datasets docs:

```bash
cd datasets
uv sync --all-extras
uv run ./dev/build-flwr-datasets-docs.sh
```

Do not commit `framework/docs/build/`, datasets docs `build/`, wheel files, or
other generated build outputs. Commit generated source/reference files only when
that is part of the documented docs workflow and the diff is intentional.

## Public API exposure mistakes

**Typical symptoms**

- `from flwr.some_package import NewName` fails even though
  `flwr.some_package.new_module.NewName` exists.
- API reference docs omit a new public class/function.
- `devtool.init_py_check` or lint complains about `__all__` ordering.
- A public import works only through an implementation module.

**Likely cause**

The public API is defined by recursive `__all__` exports, not merely by module
existence. A symbol must be imported in the appropriate `__init__.py` and listed
in `__all__` to be public. Exposing implementation modules instead of stable
symbols creates compatibility risk.

**Recovery**

1. Add the public import in the nearest package `__init__.py` using the local
   style (`from .module import Name as Name`).
2. Add `"Name"` to `__all__` and keep the list sorted.
3. Add/update a public import-path test near the changed package.
4. Update API or narrative docs when the public surface changed.
5. Run the repository check from `framework/`, then run the bundled
   importability check from the same checkout:

```bash
cd framework
uv run --no-sync --python=3.11.14 python -m devtool.init_py_check py/flwr
python ../skills/disco/flower/sub-skills/repository-maintenance/scripts/check_public_api.py flwr
```

For Flower Datasets, run analogous commands from `datasets/` in an
environment where `flwr_datasets` is importable:

```bash
cd datasets
uv run python -m devtool.init_py_check flwr_datasets
python ../skills/disco/flower/sub-skills/repository-maintenance/scripts/check_public_api.py flwr_datasets
```

If the symbol is intentionally private, do not add it to `__all__`; route users
to a public wrapper or document the private status in review feedback.

## Dev environment versus runtime environment confusion

**Typical symptoms**

- `flwr` and `flwr_datasets` import successfully, but `docsig`, `paracelsus`,
  `clang-format`, `pytest-cov`, `twine`, or docs commands are missing.
- Package CLI help works, but `./dev/test.sh` fails before tests start.
- Ray/simulation tests stall under `uv run`.
- Datasets dependency changes were made with ad-hoc pip commands and the lockfile
  is stale.

**Likely cause**

A base runtime install is not a contributor environment. The inspection setup for
this skill verified editable base installs only; it intentionally skipped dev
groups, Ray simulation extras, ML-framework-specific example dependencies,
mobile/cloud toolchains, and credentials-backed workflows.

**Recovery**

Framework contributor work:

```bash
cd framework
uv sync --locked --python=3.11.14 --all-extras --all-groups
uv run --no-sync --python=3.11.14 ./dev/test.sh false
```

Datasets contributor work:

```bash
cd datasets
uv sync --all-extras
uv run ./dev/test.sh
```

For Ray/simulation tests, mirror the framework script's stall avoidance:

```bash
RAY_ENABLE_UV_RUN_RUNTIME_ENV=0 uv run --no-sync --python=3.11.14 python -m pytest py/flwr/path/to_simulation_test.py
```

Use package project dependency commands (`uv add`, `uv add --dev`,
`uv add --optional <extra>`, `uv lock`) and commit intentional lockfile changes.

## E2E and service-check side effects

**Typical symptoms**

- E2E scripts leave generated certificates, sqlite databases, or mutated
  `pyproject.toml` files.
- Later tests fail because background SuperLink/SuperNode processes or ports are
  still active.
- A maintainer ran an e2e app directory with unrelated local edits and now sees
  confusing diffs.

**Likely cause**

`framework/e2e/*` scripts are repo-owned checks but they are not the default safe
unit-test route. They can mutate app-local files, create state, and start
services.

**Recovery**

Prefer targeted unit tests first. Run e2e scripts only when the change actually
touches local-run/deployment behavior and the worktree/app directory is isolated.
Before and after execution, inspect diffs and process/port state. Common e2e
commands are documented from an app directory, for example:

```bash
python simulation.py
./../test_superlink.sh e2e-bare
./../test_superlink.sh e2e-bare sqlite
```

If an e2e script was run accidentally, stop background services, remove generated
certificates/databases if they are untracked, and restore unrelated app config
changes before continuing.

## Generated schema documentation drift

**Typical symptoms**

- Framework test output fails in the SQLAlchemy schema documentation check.
- `framework/py/flwr/supercore/state/schema/README.md` is stale after table
  metadata changes.

**Likely cause**

The framework test script checks generated schema docs with `paracelsus inject
--check`; the format script regenerates the docs.

**Recovery**

```bash
cd framework
uv run --no-sync --python=3.11.14 ./dev/format.sh
uv run --no-sync --python=3.11.14 ./dev/check-migrations.sh
```

Review the generated schema documentation diff together with the metadata and
migration diff. Do not commit unrelated formatter output from broad formatting
unless it belongs in the same PR.
