# Troubleshooting SQL analysis

Use this table before retrying expensive model calls. Keep recovery steps safe by default: inspect metadata, narrow the schema, preserve `safe_mode=True`, and avoid app/service launches unless explicitly requested.

| Symptom | Likely cause | Recovery steps |
| --- | --- | --- |
| `ModuleNotFoundError` or import failure when importing `SQLDatabaseAgent` | The installed environment is missing a runtime dependency imported by the package, commonly notebook/display or LangChain/LangGraph components. | Use the repository skill's environment check first. Install the package's base dependencies plus notebook display support in the active environment. Re-run the bundled smoke script before attempting an LLM-backed workflow. |
| `Only read-only SELECT queries are allowed (safe_mode=True).` | The generated SQL is empty or begins with `WITH`, `SHOW`, `DESCRIBE`, `EXPLAIN`, DDL, or another non-`SELECT` form. | Prefer `get_database_metadata` for metadata tasks. Re-ask for a single plain `SELECT` query. Keep `safe_mode=True`. Do not bypass unless the user explicitly approves and the database account is read-only. |
| `Write operations are not allowed; ensure the query is read-only (safe_mode=True).` | The generated SQL contains blocked substrings such as `insert`, `update`, `delete`, `drop`, `alter`, `truncate`, `create`, or `replace`. It may be a real write or a conservative false positive in an identifier/string. | Inspect `agent.get_sql_query_code()`. If it is a real write, refuse or ask for a read-only alternative. If it is a false positive, use a read-only database role and explicit approval before considering `safe_mode=False`; otherwise rewrite the task to avoid the offending identifier/string. |
| `get_data_sql()` returns `None` | SQL validation failed, query execution failed, or the agent was not invoked successfully. | Check `agent.get_response()` and `sql_database_error` first. Do not treat `None` as an empty table. Rerun metadata inspection and retry with exact table/column names if the error is schema-related. |
| Query says table/column does not exist | LLM hallucinated a name, metadata was too large/truncated, identifier casing/quoting was wrong, or the connection points to the wrong database/schema. | Run metadata-only inspection with `n_samples=1`. Feed exact table and column names into the user instruction. Check schema qualification and quoted identifiers. Verify the SQLAlchemy URL points to the intended database. |
| Provider context-length or token-limit error | Metadata prompt includes too many schemas, tables, columns, or sample values. | Reduce `n_samples`, connect to a narrower schema/replica/view, ask a narrower question, or enable `smart_schema_pruning=True` when an additional LLM call is acceptable. |
| Metadata inspection is slow or heavy | `get_database_metadata` samples every column and random ordering can be expensive on large tables. | Use a limited read-only schema, lower `n_samples`, run against a replica/copy, or create a task-specific database user exposing only needed tables. Avoid broad production metadata scans. |
| `connection is closed` or stale connection errors | A SQLAlchemy `Connection` was closed by caller lifecycle, app rerun, or context manager exit. | Prefer passing an `Engine` to the agent when possible, or create a fresh connection immediately before invocation and close it after use. In UI apps, rebuild connections per session/state lifecycle. |
| Human review does not pause/resume as expected | `human_in_the_loop=True` without a usable checkpointer, or recommended steps were bypassed. | Pass a LangGraph checkpointer such as `MemorySaver()` and set `bypass_recommended_steps=False`. Follow the parent workflow's human-review/resume pattern. |
| Generated SQL appears correct but results are wrong | User question was ambiguous, aggregation grain was not specified, joins were incorrect, or sample metadata hid important relationships. | Ask for the desired grain, filters, and measures. Inspect primary/foreign keys from metadata. Request a simple query first, then add joins/aggregations. Compare row counts before and after joins. |
| Result dict has unexpected orientation when converted to pandas | The package converts DataFrame output with `.to_dict()`, which returns a column-oriented mapping by default. | Convert with `pd.DataFrame(agent.get_data_sql())`. If orientation still looks wrong, inspect the raw dict keys and values before visualization. |
| Logging produced local file paths or generated code artifacts | `log=True` writes generated Python functions and errors to the chosen log directory. | Keep `log=False` for normal operation. If logging is needed, store logs in a task-approved directory and redact paths from user-facing summaries. |
| Streamlit SQL app fails during provider setup or model listing | The app pattern creates a provider model in the UI layer before invoking the SQL agent. | App setup and launch belong to `multiagent-and-app-workflows`. For SQL-only tasks, instantiate the model outside this sub-skill and pass it to `SQLDatabaseAgent`; do not launch the app by default. |
| `_validate_sql` accepts a query but safety is still uncertain | The helper is a simple string check, not a full SQL parser or permissions sandbox. | Treat validation as one layer only. Use a read-only database role, review the query, and run against a replica/disposable copy for sensitive tasks. |

## Minimal recovery order

1. Run metadata-only inspection or the bundled smoke script to verify the environment and SQL helpers.
2. Confirm the connection points to the intended database/schema and uses read-only privileges.
3. Rephrase the user request with exact table names, join keys, filters, and output columns.
4. Retry `SQLDatabaseAgent` with `safe_mode=True` and low `n_samples`.
5. Check `sql_database_error`, then inspect `sql_query_code`, then convert `data_sql` to a DataFrame.
6. Route visualization, multi-agent composition, or app service work to the appropriate sibling sub-skill.
