# Extensibility reference

Use this reference to choose and implement the smallest gptme extension mechanism that fits the task. For MCP/browser/computer specifics, use [mcp-browser-computer.md](mcp-browser-computer.md). For failure diagnosis, use [troubleshooting.md](troubleshooting.md).

## Choose plugin vs skill vs lesson vs custom tool

| Need | Prefer | Why | Validation |
| --- | --- | --- | --- |
| A standalone helper that can run outside gptme | Script tool | Simple, language-agnostic, no gptme import needed. The assistant can call it through `shell` if the script is in context. | Unit-test the script directly; document required arguments. |
| A single new gptme action with prompt instructions or argument schema | Custom `ToolSpec` | Native tool listing, block execution, file/image message support, argument metadata. | Load with `--tools +./tool.py` and run inventory. |
| Runtime integration: tools plus hooks and slash commands | Plugin | gptme discovers plugin tools/hooks/commands from configured paths or entry points. | Run [../scripts/validate_plugin_skeleton.py](../scripts/validate_plugin_skeleton.py), then inventory. |
| Share explicit workflow guidance and helper files across agents | Skill | Portable Agent Skills format; loads when the skill name is mentioned or the skill is explicitly read. | Parse/list with `gptme-util skills list` or `gptme-util skills show NAME`. |
| Auto-load concise behavioral guidance from keywords/tools | Lesson | Proactive contextual guidance; no runtime code or dependency integration. | Use `/lesson search`, `/lesson show`, or `gptme-util skills list --all`. |
| Tools implemented in another language/process or shared with other MCP clients | MCP server | External protocol boundary; tools can be reused by gptme and other MCP-capable clients. | Use `gptme-util mcp list/test/info` before enabling in agent runs. |

Difficult case: "I want a new capability that knows when files are saved, runs a checker, and also gives agents usage guidance." Use a plugin for the save hook and checker command; optionally pair it with a skill or lesson for human-readable workflow guidance. Do not put hooks into a skill: gptme skills are lightweight knowledge bundles and do not auto-register runtime code.

## Script-based tools

Use script-based tools when the helper can be called through the `shell` tool and does not need to attach files/images to messages or appear in the tool list.

Operating pattern:

1. Put the script in the workspace or skill bundle.
2. Make it safe by default: `--help`, explicit inputs, dry-run where possible, bounded timeouts, no hidden network or host mutation.
3. Include it in the prompt/context so the assistant knows it exists.
4. Keep secrets out of arguments and output.

Script tools require `shell` access. If `shell` is not allowed, use a custom `ToolSpec` or plugin tool instead.

## Custom `ToolSpec` tools

A custom tool is a top-level Python `ToolSpec` instance. gptme discovers it in modules listed by `TOOL_MODULES`, plugin tool modules, entry-point plugins, or `.py` file paths passed in `--tools`.

Minimal block-executing tool pattern:

```python
from collections.abc import Generator
from gptme.message import Message
from gptme.tools import Parameter, ToolSpec


def execute(code: str | None, args: list[str] | None, kwargs: dict[str, str] | None) -> Generator[Message, None, None]:
    name = (kwargs or {}).get("name") or "world"
    yield Message("system", f"hello {name}")


hello_tool = ToolSpec(
    name="hello",
    desc="Say hello from a custom gptme tool.",
    instructions="Use this when a greeting must be generated by the tool runtime.",
    execute=execute,
    block_types=["hello"],
    parameters=[Parameter(name="name", type="string", required=False)],
)
```

Load for quick development:

```bash
gptme --tools +./hello_tool.py "use the hello tool"
```

Production loading options:

- add the module name to `TOOL_MODULES`, keeping `gptme.tools` unless you intentionally replace built-ins;
- package it as a folder plugin;
- expose it from a `gptme.plugins` entry-point plugin.

`ToolSpec` fields that matter most:

| Field | Meaning | Notes |
| --- | --- | --- |
| `name` | Unique tool name. | MCP-style dotted names are valid for grouped tools. |
| `desc` | Short description. | Appears in prompts and inventories. |
| `instructions` / `instructions_format` | Tool-use guidance. | `instructions_format["tool"]` can be shorter for provider-native mode. |
| `examples` | Usage examples. | Keep examples short and safe. |
| `functions` | Python helper functions exposed in the IPython-oriented prompt. | Bare callables are normalized into `ToolFunction`; annotate parameters when possible. |
| `execute` | Direct block/tool-call executor. | Receives `code`, `args`, and string-valued `kwargs`. |
| `block_types` | Markdown language tags this tool handles. | Use stable names; avoid collisions. |
| `available` / `available_hint` | Availability check and user-facing repair hint. | Keep checks fast; never call expensive services. |
| `parameters` | Provider-native argument schema. | Required for reliable `tool` format; still useful documentation in PTC. |
| `disabled_by_default` | Exclude unless explicitly allowed. | Good for signal or risky tools. |
| `hints` | Capability tags. | Useful for `hint:read-only`, `hint:destructive`, `hint:idempotent`, or `hint:closed-world`. |
| `hooks` / `commands` | Tool-owned hook and slash-command registrations. | See below before using; plugins are usually cleaner for larger integrations. |

## Slash command registration

A tool or plugin can register `/command` handlers. A handler receives `CommandContext` and should yield `Message` objects.

```python
from collections.abc import Generator
from gptme.commands import CommandContext
from gptme.message import Message
from gptme.tools import ToolSpec


def handle_status(ctx: CommandContext) -> Generator[Message, None, None]:
    ctx.manager.undo(1, quiet=True)
    yield Message("system", f"args: {ctx.full_args or '(none)'}")


tool = ToolSpec(
    name="status_helper",
    desc="Register a /my-status command.",
    commands={"my-status": handle_status},
)
```

Command handler checklist:

- accept one `CommandContext` argument;
- call `ctx.manager.undo(1, quiet=True)` when the command text should not remain in the log;
- yield `Message` objects for feedback;
- catch and report predictable failures;
- document the command in tool or plugin instructions.

## Folder plugin structure

A folder plugin is a Python package directory discovered from configured plugin paths.

```text
my_plugin/
├── __init__.py
├── tools/
│   ├── __init__.py
│   └── hello.py
├── hooks/
│   ├── __init__.py
│   └── lifecycle.py
└── commands/
    ├── __init__.py
    └── status.py
```

Configuration shape:

```toml
[plugins]
paths = ["./plugins"]
enabled = ["my_plugin"]

[plugin.my_plugin]
timeout = 30
mode = "dry-run"
```

Discovery behavior to account for:

- The plugin directory must contain `__init__.py` and should have an importable package name. Avoid hyphens in folder-plugin directory names.
- `tools/` can be a package or a directory of individual modules. Put actual public `.py` tool files under `tools/`; a package containing only `tools/__init__.py` may be discovered as empty by folder-plugin discovery.
- Hook and command modules need a `register()` function. If `hooks/` or `commands/` is a package, the package module's `register()` must perform registrations.
- `plugins.enabled` is an allowlist; if set, plugin names not listed are skipped.
- Plugin-specific config belongs under `[plugin.<name>]`; plugin init code must handle absent project config.

Run the static validator before loading untrusted plugin code:

```bash
python scripts/validate_plugin_skeleton.py ./plugins/my_plugin
```

## Entry-point plugins

Installable packages can expose a `GptmePlugin` via the `gptme.plugins` entry-point group.

```python
# src/my_gptme_plugin/__init__.py
from gptme.plugins import GptmePlugin
from gptme.tools import ToolSpec


def greet(name: str = "World") -> str:
    """Greet a person."""
    return f"Hello, {name}!"


greet_tool = ToolSpec(
    name="greet",
    desc="Greet a person by name.",
    functions=[greet],
)

plugin = GptmePlugin(
    name="my_gptme_plugin",
    tools=[greet_tool],
)
```

```toml
[project.entry-points."gptme.plugins"]
my_gptme_plugin = "my_gptme_plugin:plugin"
```

A `GptmePlugin` can provide any combination of:

- `tools`: direct `ToolSpec` instances,
- `tool_modules`: modules containing `ToolSpec` instances,
- `register_hooks`: callable that registers hooks,
- `register_commands`: callable that registers slash commands,
- `init`: callable receiving the full gptme `Config`,
- `provider`: LLM provider plugin, which is routed to the configuration-and-providers sub-skill.

Folder plugins are discovered before entry-point plugins. If the same plugin name appears in both, the folder plugin shadows the entry-point plugin.

## Hook types and signatures

Hooks are lifecycle callbacks. They run in the main execution path unless a specific registration uses async mode, so keep them fast and failure-tolerant.

Current hook type values:

| HookType member | Value | Typical signature |
| --- | --- | --- |
| `TURN_PRE` | `turn.pre` | `hook(manager)` |
| `STEP_PRE` | `step.pre` | `hook(manager)` |
| `STEP_POST` | `step.post` | `hook(manager)` |
| `TURN_POST` | `turn.post` | `hook(manager)` |
| `MESSAGE_TRANSFORM` | `message.transform` | message transform function; preserve content semantics. |
| `TOOL_EXECUTE_PRE` | `tool.execute.pre` | `hook(data: ToolExecutePreData)` |
| `TOOL_EXECUTE_POST` | `tool.execute.post` | `hook(data: ToolExecutePostData)` |
| `TOOL_TRANSFORM` | `tool.transform` | transform tool execution data. |
| `TOOL_CONFIRM` | `tool.confirm` | `hook(tool_use, preview=None, workspace=None)` returning a confirmation result. |
| `FILE_SAVE_PRE` | `file.save.pre` | `hook(log, workspace, path, content)` |
| `FILE_SAVE_POST` | `file.save.post` | `hook(log, workspace, path, content, created)` |
| `FILE_PATCH_PRE` | `file.patch.pre` | `hook(log, workspace, path, content)` or patch-specific data depending on call site. |
| `FILE_PATCH_POST` | `file.patch.post` | patch post-hook shape depending on call site. |
| `SESSION_START` | `session.start` | `hook(logdir, workspace, initial_msgs)` |
| `SESSION_END` | `session.end` | `hook(manager)` |
| `GENERATION_PRE` | `generation.pre` | `hook(messages, **kwargs)` |
| `GENERATION_POST` | `generation.post` | `hook(message, **kwargs)` |
| `GENERATION_CHUNK` | `generation.chunk` | `hook(chunk, **kwargs)` |
| `GENERATION_INTERRUPT` | `generation.interrupt` | interrupt hook. |
| `LOOP_CONTINUE` | `loop.continue` | `hook(manager, interactive, prompt_queue, no_confirm=False)` |
| `CWD_CHANGED` | `cwd.changed` | `hook(log, workspace, old_cwd, new_cwd, tool_use)` |
| `CACHE_INVALIDATED` | `cache.invalidated` | `hook(manager, reason, tokens_before=None, tokens_after=None)` |
| `ELICIT` | `elicit` | structured elicitation hook. |

Tool execution hooks use data objects in current code, not the older positional `(log, workspace, tool_use)` examples. When writing new hooks, prefer the data-object signatures for `tool.execute.pre` and `tool.execute.post`.

Register hooks programmatically:

```python
from gptme.hooks import HookType, register_hook
from gptme.message import Message


def on_session_start(logdir, workspace, initial_msgs):
    yield Message("system", "plugin initialized", hide=True)


def register():
    register_hook(
        name="my_plugin.session_start",
        hook_type=HookType.SESSION_START,
        func=on_session_start,
        priority=10,
    )
```

Tool-owned hook tuple pattern:

```python
from gptme.hooks import HookType
from gptme.tools import ToolSpec


def after_save(log, workspace, path, content, created):
    yield


tool = ToolSpec(
    name="save_observer",
    desc="Observe file saves.",
    hooks={"after_save": (HookType.FILE_SAVE_POST.value, after_save, 5)},
)
```

Hook best practices:

- Higher priority hooks run first.
- Return `None`, yield `Message` objects, or yield `StopPropagation` to stop lower-priority hooks where appropriate.
- Catch expected exceptions; hook failures should not surprise the main task.
- Keep network, browser, Docker, or model calls out of synchronous hooks unless explicitly authorized.
- Shell command hooks in config are appropriate only for `session.start` and `session.end`; other hook types carry structured data/control-flow semantics.

## Skills and lessons

Skills and lessons are knowledge mechanisms, not runtime code loading mechanisms.

| Feature | Lesson | Skill | Plugin |
| --- | --- | --- | --- |
| Trigger | Keywords, patterns, tools | Skill name appears in message or `SKILL.md` is read | Loaded by config/entry point |
| Content | Markdown guidance | `SKILL.md` plus optional colocated files | Python tools/hooks/commands/providers |
| Scripts | Not bundled as a runtime convention | Can be bundled for manual use | Can expose executable behavior through tools/commands |
| Dependencies | Document manually | Document manually | Package dependencies can be declared |
| Hooks/tools | No | No | Yes |
| Best for | Auto-loaded best practices | Explicit portable workflows | Deep runtime integration |

Skill frontmatter uses `name` and `description`. Lesson frontmatter uses a `match` section with keywords/tools. If a future task asks for a "skill that automatically runs on file save," split it: plugin for runtime hook, skill for explicit instructions, lesson for proactive reminder.
