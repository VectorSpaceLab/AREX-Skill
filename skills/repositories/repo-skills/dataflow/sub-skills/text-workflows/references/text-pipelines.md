# Text workflow map

This sub-skill covers several distinct text workflows. Pick the smallest stage that solves the task.

## Dependency tiers

| Tier | What it means | Typical stages |
| --- | --- | --- |
| Pure CPU / heuristic | No LLM call, no model download, no remote API | `general_text` filters/refiners, reasoning answer format / ground-truth / n-gram / token-length checks, Text2SQL execution checks, code file-type / length / content checks |
| Local model / embedding | Uses a local model, embedding server, database connector, or sandbox | `text_pt` filters, `KCenterGreedyFilter`, code quality scoring, retrieval, Text2QA, many Text2SQL generators |
| API / remote model | Calls an HTTP LLM endpoint or hosted backend | `PromptedGenerator` with API serving, reasoning generation, code generation, conversation synthesis, Text2SQL synthesis, text2model training flow |

Always do the pure CPU validation pass first if you can.

## Plain-text cleaning and filtering

Use this path when the source is raw text, crawled text, or mixed text noise.

Typical inputs:
- `raw_content`
- `text`
- `lines`
- `content`

Typical operators:
- `WordNumberFilter`, `BlocklistFilter`, `LanguageFilter`, `MinHashDeduplicateFilter`
- `RemoveEmojiRefiner`, `RemoveExtraSpacesRefiner`, `HtmlUrlRemoverRefiner`
- `NoPuncFilter`, `SpecialCharacterFilter`, `WatermarkFilter`, `CurlyBracketFilter`
- `PerplexityFilter`, `FineWebEduFilter`, `QuratingFilter`, `PairQualFilter` when a local model score is acceptable

Use these when you want to:
- remove duplicates, boilerplate, or malformed rows
- normalize text before prompting
- trim a corpus before synthesis

## Prompt-driven generation and translation

Use this path when a row should be turned into a response, summary, translation, or structured JSON.

Typical operators:
- `PromptedGenerator` for general prompt-to-text generation
- `FormatStrPromptedGenerator` for templated prompts with multiple fields
- `ChunkedPromptedGenerator` for long documents or file-backed inputs
- `RetrievalGenerator` for LightRAG-backed answers
- `Text2QAGenerator` for seed QA generation from text chunks
- `KCenterGreedyFilter` for representative sampling before QA generation

Common keys:
- input text: `raw_content`, `text`, or `problem`
- prompt source: `user_prompt`, `system_prompt`, or a prompt template object
- output text: `generated_content`, `generated_prompt`, `generated_question`, `generated_answer`
- structured output: `json_schema`

Rules of thumb:
- If you only need a rewrite or translation, start with `PromptedGenerator`.
- If the prompt needs several columns, use `FormatStrPromptedGenerator`.
- If the source text is long, split it before generation or use `ChunkedPromptedGenerator`.
- If the output must be machine-readable, validate with a JSON schema.

## Reasoning workflows

Use this path for math or general reasoning data that needs question filtering, answer generation, or answer quality checks.

Typical keys:
- source question: `instruction`
- gold answer: `golden_answer`
- generated reasoning: `generated_cot`
- question source flag: `Synth_or_Input`
- difficulty / category: `question_difficulty`, `question_category`

Typical operators:
- `ReasoningQuestionFilter`
- `ReasoningQuestionGenerator`
- `ReasoningAnswerGenerator`
- `ReasoningAnswerFormatterFilter`
- `ReasoningAnswerGroundTruthFilter`
- `ReasoningAnswerNgramFilter`
- `ReasoningAnswerTokenLengthFilter`
- `ReasoningAnswerModelJudgeFilter`
- `ReasoningQuestionDifficultySampleEvaluator`, `ReasoningQuestionCategorySampleEvaluator`

Workflow pattern:
1. filter invalid questions
2. expand or synthesize questions
3. generate answers or CoT
4. validate formatting and length
5. compare to ground truth or judge with a model

## Code workflows

Use this path for code instruction data, code synthesis, or code quality filtering.

Typical keys:
- source text: `input`, `instruction`, `text`, `lines`
- synthesized instruction: `generated_instruction`
- synthesized code: `generated_code`
- quality fields: `quality_score`, `quality_feedback`

Typical operators:
- `CodeCodeToInstructionGenerator`
- `CodeInstructionToCodeGenerator`
- `CodeInstructionGenerator`
- `CodeQualitySampleEvaluator`
- `CodeQualityScoreFilter`
- `CodeSandboxSampleEvaluator`
- `CodeAutoGeneratedFilter`, `CodeLengthSampleFilter`, `CodeTextCompositionFilter`, `CodeEncodedDataFilter`, `CodeDocumentQualityFilter`, `CodeFileTypeContentFilter`, `CodeGenericScoreFilter`

Important split:
- use heuristic / CPU filters to remove bad samples first
- only then run quality scoring, sandbox checks, or generation

## Conversations and SFT synthesis

Use this path for chat or instruction tuning data.

Typical operators:
- `ConsistentChatGenerator`
- `CondorGenerator`
- `CondorRefiner`
- `AlpagasusFilter`
- `SFTGeneratorSeed`

Typical keys:
- `category`
- `conversation`
- `difficulty`
- `instruction`
- `input`
- `output`

Note:
- `conversation` is usually a list of message objects with `role` and `value`.
- `CondorGenerator` and `CondorRefiner` are model-backed and can trigger downloads or API calls.

## Text2SQL workflows

Use this path for SQL synthesis, SQL-to-question augmentation, or SQL validation.

Typical keys:
- `SQL`
- `db_id`
- `question`
- `evidence`
- `prompt`
- `cot_reasoning`
- `cot_responses`
- `sql_component_difficulty`
- `sql_execution_difficulty`

Typical operators:
- `SQLExecutionFilter`
- `SQLGenerator`
- `SQLVariationGenerator`
- `Text2SQLQuestionGenerator`
- `Text2SQLPromptGenerator`
- `Text2SQLCorrespondenceFilter`
- `Text2SQLCoTGenerator`
- `Text2SQLCoTVotingGenerator`
- `SQLComponentClassifier`
- `SQLExecutionClassifier`

Workflow pattern:
1. verify the database exists and is reachable
2. validate SQL executability
3. synthesize questions, evidence, prompts, or CoT
4. classify difficulty or execution quality

## Text2Model workflow

Use `dataflow text2model` when the task is to turn local text files into QA-style data and then train an adapter.

High-level stages:
1. `init` creates `.cache/train_config.yaml` and a customizable `text_to_qa_pipeline.py`
2. `train` merges local JSON/JSONL inputs into `.cache/gpu/text_input.jsonl`
3. the text-to-QA stage writes `.cache/gpu/text2qa_step_step3.json`
4. the conversion stage writes `.cache/data/qa.json` and `.cache/data/dataset_info.json`
5. LlamaFactory training saves into `.cache/saves/text2model_cache_<timestamp>`

Warnings:
- the flow is model-backed and training-backed
- expect downloads, GPU use, and long runtime
- keep the input directory small when you are testing the workflow
