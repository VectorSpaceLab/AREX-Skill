# Registration Evaluation and Descriptor Files

## Purpose

Read this before running Torch Points3D registration evaluation scripts or
adapting descriptor-matching logic. The original helper scripts are useful
evidence but are not safe default runtime scripts because they assume external
data, checkpoint features, Open3D visualization, and specific directory layouts.

## Evaluation ingredients

A complete registration evaluation usually needs:

- Fragment or pair dataset root matching the selected data config.
- Descriptor/feature files saved by a trained model or baseline extractor.
- Ground-truth transforms or log files for a benchmark such as 3DMatch, KITTI, ETH, TUM, KAIST, or Planetary.
- A matching model/checkpoint config when descriptors are generated by Torch Points3D.
- Optional Open3D for FPFH baselines, visualization, and point-cloud I/O.
- Optional sparse backends for sparse registration model families.

## Descriptor matching concept

The source registration scripts contain utilities for matching descriptors,
computing nearest-neighbor correspondences, and evaluating fragment pairs
against ground truth. Before running such a workflow, identify:

1. Feature file naming convention and extension.
2. Whether descriptors are stored per fragment, per pair, or in a consolidated directory.
3. Ground-truth transform/log format and coordinate frame.
4. Evaluation thresholds: distance/radius, inlier ratio, recall criteria, and overlap filtering.
5. Output location for metrics, match visualizations, or saved correspondences.

## FPFH/Open3D baseline caveat

Classical FPFH extraction through Open3D can be useful as a baseline, but it is
not a Torch Points3D model smoke. It needs point-cloud files, voxel/downsample
parameters, normal estimation, and benchmark-specific fragment tables. Verify
Open3D import and data availability first.

## KITTI and 3DMatch demos

Demos that visualize or evaluate KITTI/3DMatch descriptors often assume:

- Downloaded benchmark fragments and metadata.
- A trained checkpoint or saved feature directory.
- Optional CUDA and sparse convolution dependencies.
- Display availability for visualization.

Do not run them automatically in a headless or data-free environment. Use the
FPS smoke as a utility check and then request/confirm the real dataset and
checkpoint paths.

## Minimal preflight checklist

- Does the selected `data=registration/<config>` file match the dataset root?
- Does the selected `models=registration/<family>` need a sparse backend?
- Is the checkpoint/model descriptor dimensionality known?
- Are feature files and ground-truth files present and in the same coordinate system?
- Are output writes, visualization windows, and runtime acceptable to the user?

## When to use evaluation versus `eval.py`

Use `eval.py` when the checkpoint and dataset support Torch Points3D tracker
metrics directly. Use registration-specific descriptor evaluation when the task
is about benchmark matching/recall using saved fragment features or external
baseline descriptors.
