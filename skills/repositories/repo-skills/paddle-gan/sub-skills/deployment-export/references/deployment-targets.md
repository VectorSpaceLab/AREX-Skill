# Deployment targets and boundaries

This reference maps the exported static model to the deployment targets that PaddleGAN supports in practice.

## Target summary

| Target | Good for | Required facts | Default status here |
| --- | --- | --- | --- |
| Paddle Inference Python | quick static checks and metrics | exported prefix + config + model_type | active planning target |
| Paddle Inference with TensorRT | GPU acceleration planning | TRT-enabled Paddle build and compatible CUDA/cuDNN/TRT stack | planning only until prerequisites are confirmed |
| Serving | server deployment | serving export tree and Paddle Serving runtime | reference-only unless explicitly authorized |
| Lite | mobile / edge deployment | Paddle-Lite build, Android toolchain, `.nb` conversion | reference-only unless explicitly authorized |
| C++ inference | VSR video deployment | OpenCV, Paddle Inference C++ library, and exported prefix files | reference-only unless explicitly authorized |
| TIPC | certification evidence | prepared logs and reference results | evidence-only by default |

## Paddle Inference Python

Use this for the normal static-model path.

Minimum requirements:
- exported `.pdmodel` / `.pdiparams` prefix,
- the matching config file,
- the correct `model_type` branch,
- a compatible backend selection.

This route is the default way to sanity-check an export before asking for a heavier backend.

## TensorRT planning

TensorRT is only meaningful when the installed Paddle package or inference library already includes TensorRT support.

Planning rules:
- If TensorRT symbols are missing, do not keep retrying TRT flags.
- Start with `fluid` or CPU/GPU inference.
- Only move to `trt_fp32` or `trt_fp16` after the backend is known to support it.
- Use `min_subgraph_size` to control how aggressively TensorRT rewrites the graph.
- Use dynamic-shape hints only when the exported model's input names and shape ranges are known.

Common warning patterns:
- `tensorrt_op` missing -> the wheel/lib is not TRT-enabled.
- `some trt inputs dynamic shape info not set` -> raise `min_subgraph_size` or supply the missing shape info.
- `Slice on batch axis is not supported in TensorRT` -> prefer dynamic shapes or fall back to `fluid`.

## Serving

Serving is useful when a static export must be wrapped in a service process.

Prerequisites:
- a serving export tree under the model prefix,
- Paddle Serving runtime version 0.6 or newer,
- matching client/server config files generated by the export step.

Default boundary:
- do not start the server as part of routine skill drafting,
- do not treat Serving startup as the verification default,
- use the directory layout as evidence that the export is service-ready.

What to look for:
- `serving_client/` and `serving_server/` under the exported prefix,
- a client config that lists the feed and fetch names,
- a server config that matches the same prefix.

## Lite

Lite is the mobile / edge path and is mainly relevant for the FirstOrder/FOM deployment notes in this repository.

Prerequisites:
- Paddle-Lite build or prebuilt package,
- Android NDK and Java toolchain when building the mobile demo,
- `with_cv` and `with_extra` enabled for the FOM operator coverage used here,
- `.nb` conversion from the exported static model.

Default boundary:
- keep Lite as a reference path unless the task explicitly authorizes mobile build and deployment work,
- do not start an APK or mobile-server flow by default,
- treat the Lite docs as a prerequisite map, not an execution request.

## C++ inference

The C++ deployment path in this repository is centered on the video super-resolution demo.

Prerequisites:
- exported model prefix files,
- Paddle Inference C++ library,
- OpenCV,
- matching CPU/GPU runtime libraries,
- TensorRT libraries only if the C++ build is meant to use TRT.

Default boundary:
- do not compile or run the demo as a routine drafting step,
- use the layout and constructor arguments as reference evidence,
- keep this path limited to deployment planning unless explicit runtime verification is requested.

## TIPC

TIPC is a validation harness and evidence source, not the default execution route.

What it covers here:
- Python train / export / inference chains for selected models,
- C++ inference coverage for the VSR demo,
- result comparison against stored metric logs.

Relevant harnesses:
- `test_train_inference_python.sh`
- `test_inference_cpp.sh`
- `compare_results.py`

How to use the evidence:
- inspect the config tables to see which models and backends were certified,
- use the stored result logs as a reference for expected metrics,
- do not run the heavy harnesses by default during sub-skill drafting.

## Recommended decision rule

1. Need a static export or exported model check -> use the bundled export wrapper and checker.
2. Need quick inference planning -> use Paddle Inference Python.
3. Need speed planning on GPU -> evaluate TensorRT only if the backend is present.
4. Need server/mobile/C++ deployment -> switch to the target-specific reference path and confirm prerequisites first.
5. Need validation evidence -> consult the TIPC harness mapping, but do not run heavy jobs unless explicitly asked.
