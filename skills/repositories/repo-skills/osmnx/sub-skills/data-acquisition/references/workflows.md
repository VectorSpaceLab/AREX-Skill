# Data acquisition workflows

This reference explains how to choose the right OSMnx acquisition function, what each one returns, and which settings matter before the first request.

## Core function map

| Function | Use when | Important parameters | Output |
| --- | --- | --- | --- |
| `geocode(query)` | You only need a point for an address/place name. | `query` string. | `(lat, lon)` tuple. |
| `geocode_to_gdf(query, which_result=None, by_osmid=False)` | You need a boundary polygon or an OSM element by name/ID. | `query`, `which_result`, `by_osmid`. | GeoDataFrame with place geometry and metadata. |
| `graph_from_bbox(bbox, ...)` | You already have a bounding box. | `bbox`, `network_type`, `custom_filter`, `simplify`, `retain_all`, `truncate_by_edge`. | `nx.MultiDiGraph`. |
| `graph_from_point(center_point, dist, ...)` | You want a graph around a center point. | `center_point`, `dist`, `dist_type`, `network_type`, `custom_filter`. | `nx.MultiDiGraph`. |
| `graph_from_address(address, dist, ...)` | You want a graph around an address. | `address`, `dist`, `dist_type`, `network_type`, `custom_filter`. | `nx.MultiDiGraph`. |
| `graph_from_place(query, ...)` | You want a graph inside a place boundary. | `query`, `which_result`, `custom_filter`. | `nx.MultiDiGraph`. |
| `graph_from_polygon(polygon, ...)` | You already have a valid boundary geometry. | `polygon`, `network_type`, `custom_filter`. | `nx.MultiDiGraph`. |
| `graph_from_xml(filepath, ...)` | You already have local raw OSM XML. | `filepath`, `bidirectional`, `simplify`, `retain_all`, `encoding`. | `nx.MultiDiGraph`. |
| `features_from_bbox(bbox, tags)` | You want features in a bounding box. | `bbox`, `tags`. | GeoDataFrame. |
| `features_from_point(center_point, tags, dist)` | You want features around a point. | `center_point`, `tags`, `dist`. | GeoDataFrame. |
| `features_from_address(address, tags, dist)` | You want features around an address. | `address`, `tags`, `dist`. | GeoDataFrame. |
| `features_from_place(query, tags, which_result=None)` | You want features inside a place boundary. | `query`, `tags`, `which_result`. | GeoDataFrame. |
| `features_from_polygon(polygon, tags)` | You already have a valid boundary geometry. | `polygon`, `tags`. | GeoDataFrame. |
| `features_from_xml(filepath, ...)` | You already have local raw OSM XML and want feature extraction without Overpass. | `filepath`, optional `polygon`, optional `tags`, `encoding`. | GeoDataFrame. |

## How to choose the geometry

### Bounding box

Use a bbox when the user already has four coordinates or wants the simplest query.

- Input order: `(left, bottom, right, top)`.
- Coordinates must be unprojected latitude/longitude degrees (`EPSG:4326`).
- Good for explicit map windows and for planning queries where the area is already known.

### Point

Use a point when the user wants “around here” data.

- Input order: `(lat, lon)`.
- Add `dist` in meters.
- `dist_type="bbox"` keeps the geographic square around the point.
- `dist_type="network"` truncates by network distance from the nearest node after the bbox graph is built.

### Address

Use an address when the user has a street address but not a map boundary.

- OSMnx geocodes the address to a point first.
- Then it follows the same logic as `graph_from_point` or `features_from_point`.
- If the geocode result is bad, use a more specific address or switch to `geocode_to_gdf` for inspection.

### Place

Use a place when the user wants a named boundary such as a neighborhood, city, county, or region.

- OSMnx geocodes the query to a place boundary.
- For graphs and features, the place must resolve to a Polygon or MultiPolygon.
- If the query resolves to a point instead, use the address workflow or pick a different `which_result`.

### Polygon

Use a polygon when you already have a valid Shapely boundary.

- Polygon input must be valid.
- It must be a Polygon or MultiPolygon in `EPSG:4326`.
- This is the most precise option for precomputed study areas.

### XML

Use XML when the data is already downloaded locally.

- `graph_from_xml` and `features_from_xml` can read `.osm`, `.bz2`, and `.gz` OSM XML files.
- This is the offline fallback when you do not want to contact Nominatim or Overpass.
- `graph_from_xml` is for raw OSM XML, not for XML previously generated by OSMnx.
- If you need to persist an OSMnx graph for later reuse, route that task to `graph-modeling-io` instead.

## Geocoding workflow

### `geocode(query)`

- Returns a single `(lat, lon)` pair.
- Use it when you only need a center point.
- If the query cannot be matched, expect `InsufficientResponseError`.

### `geocode_to_gdf(query, which_result=None, by_osmid=False)`

- Returns a GeoDataFrame with the matched OSM element.
- Use `which_result=1` when you want the top-ranked match regardless of geometry type.
- Use `which_result=None` when you want the first Polygon/MultiPolygon match.
- Use `by_osmid=True` only with string IDs such as `N...`, `W...`, or `R...`.
- For list queries, pass a list of `which_result` values with the same length.

## Graph acquisition workflow

Graph acquisition means constructing a networked `MultiDiGraph` from Overpass or local XML.

### Network type and custom filter

- `network_type` selects the built-in graph filter family: `all`, `all_public`, `bike`, `drive`, `drive_service`, or `walk`.
- `custom_filter` replaces the built-in network type filter.
- If `custom_filter` is a string, OSMnx intersects those conditions.
- If `custom_filter` is a list, OSMnx unions the alternative filters.
- Use a `network_type` in `settings.bidirectional_network_types` when you want the graph to be fully bidirectional.

### Output expectations

- The graph is created in `EPSG:4326`.
- Nodes should have `x`, `y`, and `street_count`.
- Edges should have `osmid` and `length`.
- The returned graph may be simplified unless `simplify=False` is passed.

### Practical choice notes

- Use `graph_from_bbox` for explicit map windows and debug-friendly plans.
- Use `graph_from_point` or `graph_from_address` when the user cares about proximity to a center rather than a boundary.
- Use `graph_from_place` when the user wants the official place boundary.
- Use `graph_from_polygon` when the study area is already a valid polygon.
- Use `graph_from_xml` for offline local raw OSM data.

## Feature acquisition workflow

Feature acquisition means constructing a GeoDataFrame of OSM elements such as building footprints, amenities, transit stops, or other tag-matched features.

### Tag semantics

The `tags` argument is a dictionary whose values mean:

- `True` → any value for that key.
- `str` → one exact `key:value` match.
- `list[str]` → any of those values.

Examples:

```python
{"building": True}
{"landuse": ["retail", "commercial"], "highway": "bus_stop"}
```

Important detail: results are the union of the requested tag matches, not the intersection. A feature only needs to match one requested tag branch.

### Feature geometry and relations

- Closed ways may be interpreted as polygons when their tags imply polygon geometry.
- Only boundary and multipolygon relations are handled.
- If no matching features remain after filtering, OSMnx raises `InsufficientResponseError`.

### Output expectations

- The final GeoDataFrame is indexed by `element` and OSM ID.
- Feature geometry is in `EPSG:4326`.
- `features_from_xml` can skip spatial/tag filtering when `polygon=None` and `tags=None`.
- `features_from_xml` drops XML metadata columns such as `changeset`, `timestamp`, `uid`, `user`, and `version` after parsing.

## Historical and cache-aware workflow

For reproducible historical queries or no-network planning:

```python
import osmnx as ox

ox.settings.use_cache = True
ox.settings.cache_folder = "./cache"
ox.settings.requests_timeout = 180
ox.settings.overpass_rate_limit = True
ox.settings.overpass_settings = '[out:json][timeout:90][date:"2019-10-28T00:00:00Z"]'
```

Useful patterns:

- Set `settings.use_cache=True` to reuse earlier HTTP responses.
- Set `settings.cache_only_mode=True` when you want to warm the cache only. This intentionally stops after the response is saved and raises `CacheOnlyInterruptError`.
- Keep `settings.overpass_rate_limit=True` when using public Overpass.
- Use `settings.overpass_url` and `settings.nominatim_url` only when you need a custom instance.
- Use `settings.requests_kwargs` for proxies, certificates, or other advanced `requests` options.

### Historical building-footprint plan

For a historical building-footprint task, prefer this sequence:

1. Identify the place boundary or polygon first.
2. Set the Overpass date in `settings.overpass_settings`.
3. Use `features_from_place` or `features_from_polygon` with `tags={"building": True}`.
4. If you only need to cache the response now, enable `cache_only_mode=True` and treat the interrupt as expected.
5. If the query is large, expect OSMnx to subdivide it automatically via `max_query_area_size`.

## Validation checkpoints

- Confirm the geometry type before querying.
- Confirm bbox order and point coordinate order.
- Confirm tags are broad enough to match the intended features.
- Confirm `which_result` is appropriate for ambiguous geocodes.
- Confirm the output family: graph, GeoDataFrame, or point tuple.
- If the task turns into graph cleaning, projection, persistence, routing, or plotting, route it away from this sub-skill.
