# Precision inference and bit-exact propagation

Use this reference when a config already exists and the task is to choose, inspect, or validate hls4ml numeric types.

## Config hierarchy

Precision and reuse settings are read in this order:

1. `Model`: model-wide defaults.
2. `LayerType`: overrides for all layers of a type.
3. `LayerName`: layer-specific overrides; use this for precision tuning.
4. Named precision variables inside a layer, such as `weight`, `bias`, `accum`, `result`, `exp_table`, or backend/layer-specific type names.

Example paths:

```python
config["Model"]["Precision"]["default"] = "fixed<16,6>"
config["Model"]["ReuseFactor"] = 1
config["LayerName"]["dense1"]["Precision"]["weight"] = "fixed<8,4>"
config["LayerName"]["dense1"]["Precision"]["result"] = "auto"
config["LayerName"]["dense1"]["ReuseFactor"] = 4
```

Run `scripts/inspect_precision_config.py` when you need to see the exact key layout generated by the installed package.

## Automatic precision inference

Automatic precision inference is initiated by setting a **layer-level** precision to `"auto"`. Do not set model-level `Precision` to `"auto"`; the model default must be an explicit precision such as `fixed<16,6>` or `ap_fixed<16,6>`.

Good starting point:

```python
config = hls4ml.utils.config_from_keras_model(
    model,
    granularity="name",
    backend="Vivado",
    default_precision="fixed<16,6>",
    default_reuse_factor=1,
    max_precision="fixed<24,12>",  # optional cap
)
```

Equivalent per-layer configs are available from the ONNX and PyTorch helpers. Pass the backend when generating `granularity="name"` configs so backend-specific configurable precision attributes are included. The `config_from_*` helpers often populate layer precision fields as `"auto"` at this granularity when a configurable type has no fixed default.

Operational behavior:

- The inference pass computes conservative accumulator/result widths from input and weight bit widths, not from observed values.
- Quantizer-derived layer metadata can set `weight`, `bias`, or `result` precision directly instead of leaving them as `auto`.
- `max_precision` caps the total width and integer width separately; it is useful when conservative inference grows too wide.
- `compile()` is a fast validation gate: if any required type remains unspecified after inference, compilation fails before prediction.
- Use profiling and `predict()` parity after compile because a type that is representable can still be too narrow for model accuracy.

## Manual precision edits

Use manual edits when profiling shows overflow or loss of fractional accuracy, or when automatic inference is too conservative.

Typical edits:

```python
# tighten weights while keeping accumulator inferred
config["LayerName"]["dense1"]["Precision"]["weight"] = "fixed<8,3>"
config["LayerName"]["dense1"]["Precision"]["accum"] = "auto"

# widen an activation/result that clips in profiling
config["LayerName"]["relu1"]["Precision"]["result"] = "fixed<18,8>"
```

Avoid adding rounding/saturation to accumulators unless you have measured the tradeoff; accumulator rounding/saturation can increase generated-code cost. For outputs, weights, or activation tables, rounding and saturation modes may be appropriate if the numerical comparison supports them.

## Model-wise bit exactness

`bit_exact` activates model-wise precision propagation. Unlike layer-level `auto`, it attempts to infer all precisions from embedded quantizer information and raw weights, and it ignores user-provided precision settings.

Public conversion knobs:

```python
hls_model = hls4ml.converters.convert_from_keras_model(
    model,
    hls_config=config,
    backend="Vivado",
    bit_exact=True,   # True, False, or None
)

hls_model = hls4ml.converters.convert_from_onnx_model(
    onnx_model,
    hls_config=config,
    backend="Vitis",
    bit_exact=True,
)
```

Source behavior to rely on:

- `bit_exact=None` may enable the pass automatically when fixed-point quantizer proxy layers are present.
- The documentation/source describe automatic enablement for supported HGQ/HGQ2 and PQuantML models unless disabled, and QKeras can set the key automatically for supported quantized models.
- The public PyTorch converter signature in this checkout does not expose a `bit_exact` keyword, so PyTorch tuning usually stays in layer-level auto/manual precision territory unless a later wrapper adds that capability.
- QONNX bit-exact support is not yet source-promised in this checkout; treat it as experimental unless a later verification cycle proves it on the target model.
- The flow is intended for fixed-point-compatible quantized models. Non-fixed-point quantizers or unquantized arithmetic may only match approximately, grow to very large widths, or fail conversion.
- Automatic precision inference and model-wise bit-exact propagation should not be mixed in the same tuning plan.
- Quantizers should appear immediately after model inputs when input precision must be inferred; otherwise the input may remain too wide or be inferred incorrectly.
- Unsupported operators deliberately crash or warn rather than silently producing a false bit-exact claim.

## Validation checklist

Before claiming a precision change works:

1. Regenerate or edit a `granularity="name"` config with backend specified.
2. Decide whether this run uses layer-level `auto` **or** `bit_exact`; do not treat them as interchangeable.
3. Convert and run `compile()`.
4. Compare `hls_model.predict(X)` with the frontend model on representative data.
5. If parity fails, enable per-layer `Trace=True` and use profiling/compare tools to find the first divergent layer.
6. If a quantized model is claimed bit-exact, require exact array equality on representative exact-grid inputs; otherwise state the tolerance and why exact equality is not expected.
