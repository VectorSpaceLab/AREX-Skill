# Troubleshooting advanced extension and tool workflows

Use this matrix after the task has been routed to this sub-skill. For package installation, backend installation, cache cleanup, or compiler provisioning, route to runtime/setup guidance first.

| Symptom | Likely cause | Diagnose safely | Recovery |
| --- | --- | --- | --- |
| `jt.code` or a custom op fails before running any kernel | C++ compiler missing, unsupported, or not selected by Jittor. | Run the bounded smoke in import mode: `python scripts/custom_op_smoke.py --skip-compile`. If compile is needed, run default CPU smoke and inspect the compiler error without changing backend flags. | Install/select a supported C++ compiler in the runtime environment, then rerun the tiny CPU smoke before scaling. Do not treat CUDA setup as required for CPU custom code. |
| C++ source syntax error in `jt.code` | Inline `cpu_src`, `cuda_src`, or `cpu_header` has invalid C++/CUDA, missing braces, missing includes, or macro misuse. | Reduce to a one-output, one-input tiny snippet. Confirm use of `@in0(...)`, `@out(...)`, `@ARGS_DEF`, `@PRECALC`, and `@ARGS` matches CPU vs CUDA context. | Add required includes to `cpu_header`/`cuda_header`; compile one branch at a time; keep generated source strings short until the minimal case compiles. |
| Custom op compilation reports missing header/source pair | `compile_custom_ops` filenames do not follow paired `*_op.h` plus `*_op.cc`/`.cpp`/`.cu` convention, or class name does not match op basename. | Check file basenames and op type names before compiling. For a single op, prefer `compile_custom_op` with `warp=True` while prototyping. | Rename pairs consistently, ensure header/source counts match, and keep `name()` returning the Python op name expected by callers. |
| Output shape mismatch | Python-declared output shape does not match writes in `jt.code`, custom op constructor creates wrong shape, or dynamic shape max is too small. | Print/inspect input shapes in Python before compiling; verify tiny inputs; for dynamic outputs, assert max shape and actual `set_shape` values. | Compute shape in Python first, pass it explicitly, and add small assertions before writing the kernel. For dynamic shapes, allocate a safe maximum and set the actual shape once. |
| Dtype mismatch or wrong numeric values | Output dtype string is wrong, custom op `jit_prepare` uses the wrong dtype define, casts are missing, or integer/float literals are unintended. | Check `x.dtype`, requested output dtype, and expected NumPy dtype with a tiny deterministic array. | Use input `.dtype` when the output should match, explicit strings such as `"float32"` when it should not, and explicit C++ casts for literals. |
| Gradients are missing or wrong | `cpu_grad_src`/`cuda_grad_src` list does not align with inputs, saved variables are wrong, or only the forward code was implemented. | Test forward first, then wrap the code op in a tiny `jittor.Function` and compare gradients against a simple analytic expected value. | Add one gradient source per differentiable input or implement `Function.grad`; keep non-differentiable inputs out of the gradient list. |
| CUDA code fails on a CPU-only runtime | A `cuda_src` branch or custom op CUDA branch is being forced without CUDA support. | Check `jt.compiler.has_cuda` or `jt.has_cuda`; run CPU smoke separately. | Guard CUDA runs with CUDA availability and `jt.flag_scope(use_cuda=1)`. Provide `cpu_src`/`JIT_cpu` branch for portable verification. If CUDA is required by the user, move backend setup to runtime guidance first. |
| CUDA source compiles but values differ from CPU | CUDA indexing, stride, block/grid sizing, or dtype assumptions differ from CPU code. | Use a small 1-D input and compare CPU and CUDA results under separate scopes. Then grow dimensions one axis at a time. | Mirror CPU indexing carefully, use `@PRECALC` and `@ARGS` macros, and verify shape variables such as `in0_shape0` and `in0_shape1`. |
| C++ console compile command fails with C++ standard errors | Compiler does not support C++17 or flags are missing. | Run `python scripts/jittor_console_flags.py --mode command` and inspect whether `--cxx-flags` is included in the command. | Use a C++17-capable compiler and include generated C++ flags. Do not manually drop the standard flag unless replacing it with an equivalent. |
| C++ console link fails with Python library errors | Active Python does not expose a linkable dynamic library, `--libs-flags` could not locate it, or the compiled binary cannot find `libpython` at launch. | Run `python scripts/jittor_console_flags.py --mode flags` and look for a clear `Python dynamic library` failure; if compile succeeds but launch fails with `libpython*.so` not found, run from the same environment or expose that environment's Python library directory to the dynamic linker. | Use an environment/Python build that includes a shared Python library and regenerate flags in that same environment. Do not hard-code library paths from another machine. |
| C++ console binary runs but array exchange fails | `get_array<T, NDIM>` type/dimension does not match the Python variable, the embedded snippet did not create the expected variable name, or Jittor's internal compiler helper spawned a Python interpreter that cannot import `jittor_utils`. | Start with scalar `set/get`, then a tiny `jittor::array` round trip. If the error names `asm_tuner.py` or `ModuleNotFoundError: jittor_utils`, confirm the same Python environment is used for Jittor, `jittor_utils.config`, and the launched binary. | Match template type and dimension exactly, keep names consistent, and remove model-heavy code until the array path works. If the helper Python is inconsistent, reinstall or regenerate console flags from the intended environment before treating the console API as broken. |
| `jittor_utils.config --help` mentions `--link-flags`, but link flags fail | Help wording and implemented flag name can differ. | Use the same command shape as the bundled wrapper: `--include-flags --libs-flags --cxx-flags`. | Prefer `scripts/jittor_console_flags.py`; if calling the module directly, use `--libs-flags` for the link step. |
| Converter output imports or calls unsupported APIs | PyTorch converter mapping is incomplete for that code. | Convert a small source fragment and read the generated code before running it. | Manually replace unsupported pieces with Jittor APIs, then run a tiny parity test. Do not assume source-to-source conversion is semantically complete. |
| Converter parity test needs PyTorch, pretrained weights, or network access | Test design copied a heavyweight model workflow or uses `pretrained=True`. | Check whether the comparison imports PyTorch or downloads weights. | Use `pretrained=False`, synthetic inputs, and optional PyTorch only when comparison is explicitly requested and installed. |
| Converter server cannot start | Flask is not installed, Docker/service scripts are not available, or network/listener permissions are blocked. | Prefer direct `convert(...)` use. Only inspect service dependencies if the user explicitly requested a server. | Install Flask/Docker/network prerequisites only under an explicit service deployment task. Do not start a listener as a smoke test. |
| Unsafe service script or background loop appears in suggested workflow | The task has drifted from local conversion into service deployment. | Ask whether the user intends to run a public or local service. | Keep default workflow local and bounded. If service deployment is required, document host, port, authentication, network, and shutdown plan before running anything. |

## Minimal recovery ladder

1. Run `python scripts/custom_op_smoke.py --help` or `python scripts/jittor_console_flags.py --help` to verify the wrapper interface without importing Jittor or compiling.
2. Run `python scripts/custom_op_smoke.py --skip-compile` to check public API names.
3. Run the default CPU smoke to prove `jt.code` can compile and execute on CPU.
4. Only then add custom op classes, multi-output code, gradients, C++ console compilation, or CUDA branches.
5. Keep CPU and CUDA results as separate evidence in reports and user-facing claims.
