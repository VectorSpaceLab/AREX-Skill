# EasyTool Data and Layout Reference

EasyTool relies on relative files under the checkout's `easytool/` directory. Run commands from that directory unless you deliberately reproduce the same relative layout elsewhere.

## Expected source layout

```text
easytool/
  main.py
  data_process.py
  requirements.txt
  easytool/
    util.py
    funcQA.py
    restbench.py
    toolbench.py
    toolbench_retrieve.py
  data_funcqa/
    funchub/math.py
    tool_instruction/functions_data.json
    tool_instruction/tool_dic.jsonl
    test_data/                  # generated by data_process.py
  data_restbench/
    tool_instruction/tmdb_tool.json
    test_data/                  # generated by data_process.py
  data_toolbench/
    tool_instruction/toolbench_tool_instruction.json
    tool_instruction/API_description_embeddings.zip
    tool_instruction/API_description_embeddings.pkl  # extracted locally for retrieve
    test_data/                  # generated by data_process.py
  toolenv/tools/                # external ToolBench tool code, not bundled by EasyTool
```

The source default for `--tool_root_dir` is `.toolenv/tools/`, while documented commands use `./toolenv/tools`. Pass `--tool_root_dir` explicitly.

## FuncQA schemas

### Tool instructions

`data_funcqa/tool_instruction/functions_data.json` is a dictionary keyed by string IDs. Each value has:

- `ID`: numeric tool ID.
- `standardized_name`: function name in `data_funcqa/funchub/math.py`, such as `add_`.
- `API_description`: natural-language tool description.
- `Usage`: object with `required_parameters` and an `Example` containing scenario and parameters.

`data_funcqa/tool_instruction/tool_dic.jsonl` is JSON Lines. Each line has at least:

- `ID`: numeric tool ID.
- `description`: compact description shown to the model for tool choice.

### Test data

Generated FuncQA files are:

- `data_funcqa/test_data/funcqa_mh.json`
- `data_funcqa/test_data/funcqa_oh.json`

The execution code expects each test item to contain `question`.

### Outputs

FuncQA writes one JSON object per line with fields such as `ID`, `question`, `final_answer`, `subtask`, `answer_subtask`, `answer_wrong`, `check_index`, `execute_log`, and `check`. `execute_log` contains lists for API selections, call results, tool-check reasons, and tool instructions.

## RestBench schemas

`data_restbench/tool_instruction/tmdb_tool.json` is a list. Each tool object has:

- `ID`: numeric ID used in the model-selected task path.
- `tool_name`: REST endpoint name.
- `tool_description`: natural-language guidance.
- `tool_usage`: compact usage string, for example a `GET ...` path.
- `Example`: scenario and parameters.

Generated test data is `data_restbench/test_data/tmdb.json`. The execution code expects each item to contain `query`.

RestBench output JSONL rows include `ID`, `question`, `task_path`, and `tool_choice_ls`. In this source branch, RestBench maps model-selected IDs to usage strings; it does not import external API tool code.

## ToolBench schemas

### Tool instructions

`data_toolbench/tool_instruction/toolbench_tool_instruction.json` is a dictionary keyed by string IDs. Each value has:

- `ID`: numeric ID.
- `tool_name`: display name.
- `tool_description`: long tool description.
- `tool_guidelines`: dictionary keyed by API names, with per-API usage guidance.

For actual calls, the selected tool's `standardized_name` is used internally when looking up external tool code. The API function name is normalized with `standardize()` and `change_name()` before dispatch.

### Generated test data

Generated files are:

- `data_toolbench/test_data/G2_category.json`
- `data_toolbench/test_data/G3_instruction.json`

`data_process.py` expects downloaded ToolBench test items to contain an `api_list` of tools. It adds a `Tool_dic` field to each item. Each `Tool_dic` entry has:

- `ID`: ID from `toolbench_tool_instruction.json`.
- `Description`: the selected tool description.

The execution code expects each generated test item to contain `query` and, for direct ToolBench, `Tool_dic`.

### ToolBench retrieval embeddings

`toolbench_retrieve.py` opens `data_toolbench/tool_instruction/API_description_embeddings.pkl`, which is extracted from `API_description_embeddings.zip`. The pickle is expected to load as `(filenames, embedded_texts)`. Retrieval computes a fresh OpenAI embedding for each question/subtask and selects the top five filenames from the local embedding matrix.

### External `toolenv/tools` layout

The ToolBench call path scans `--tool_root_dir` recursively. For a selected standardized tool name `A`, it expects to find a directory named `A` and import:

```text
<tool-root>/<possibly-nested-parent>/<A>/api.py
```

The imported module must define a callable for the normalized selected API name. EasyTool passes model-generated parameters as keyword arguments and also injects `toolbench_rapidapi_key` from `RAPIDAPI_KEY`.

If the tree is missing or the directory names do not match standardized names, ToolBench can still run through model prompts but selected calls return empty or fail, causing retries and possible blank call results.

## Progress and output files

Progress files are plain-text integer files in the current working directory:

| Workflow | Progress value meaning | Progress filename |
| --- | --- | --- |
| FuncQA | next index in `test_data[start_index:]` | `FuncQA_<data_type>_<model>_Easytool.txt` |
| RestBench | next index in `tmdb.json` | `restbench_<model>_Easytool.txt` |
| ToolBench direct | next index in `G2_category.json` or `G3_instruction.json` | `<data_type>_<model>_Easytool.txt` |
| ToolBench retrieve | same as ToolBench direct | `<data_type>_<model>_Easytool.txt` |

Output JSONL files are append-only. Clean starts require either a clean working directory or explicit removal/archival of old output and progress files.

## Data that should not be bundled into skills

Do not copy full FuncQA, RestBench, ToolBench generated datasets, embedding pickles, or `toolenv/tools` code into generated skill runtime docs. Keep only schema guidance and safe helpers. The datasets and external tool code can be large, network-provided, credential-dependent, or outside EasyTool's repository boundary.
