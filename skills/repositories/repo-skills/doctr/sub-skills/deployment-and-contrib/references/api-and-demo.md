# API, demo, and Docker guidance

This reference covers docTR's optional deployment and demo surfaces. Prefer direct package APIs for most research and batch work; use these surfaces when the user specifically needs an HTTP service, an interactive browser demo, or container packaging.

## Choosing the right surface

| Need | Recommended surface | Why | Avoid when |
|---|---|---|---|
| One-off OCR/KIE, notebooks, batch scripts, tests | Package API through `DocumentFile`, `ocr_predictor`, or `kie_predictor` | Lowest overhead, easiest to debug, no server lifecycle | The user needs a shared HTTP boundary or UI |
| Integrating docTR behind an HTTP endpoint | FastAPI template pattern | Provides OpenAPI docs, multipart upload handling, typed query parameters, and JSON responses | The task is only local inference or needs strict production hardening not yet designed |
| Letting humans inspect one document interactively | Streamlit demo pattern | Exposes model/threshold options, segmentation heatmap, visual overlay, reconstitution, table display, and JSON output | The task is automation, high throughput, or headless deployment |
| Reproducible runtime or GPU-enabled shell | Docker image | Encapsulates OS packages, Python, docTR extras, and CUDA-ready base image | The host lacks compatible container/GPU support or the user only needs a Python package install |

## FastAPI template shape

The template application is a small FastAPI service around docTR predictors:

- application metadata comes from the package version and a static project title/description;
- route groups are included at `/recognition`, `/detection`, `/ocr`, and `/kie`, each with a POST handler at the route root;
- request parameters are Pydantic models exposed as query parameters through FastAPI dependency injection;
- uploads are multipart `files` with accepted MIME types `image/jpeg`, `image/png`, and `application/pdf`;
- PDFs are expanded into one image array per page, and filenames are repeated across page results;
- unsupported MIME types raise a request error instead of silently trying to parse arbitrary bytes;
- an `X-Process-Time` response header records request processing time;
- OpenAPI/Swagger and ReDoc are generated by FastAPI once the service is running.

### Route responsibilities

| Route prefix | Predictor path | Important query fields | Response shape |
|---|---|---|---|
| `/detection` | build `ocr_predictor(pretrained=True, ...)`, then use its detection predictor | `det_arch`, `assume_straight_pages`, `preserve_aspect_ratio`, `symmetric_pad`, `det_bs`, `bin_thresh`, `box_thresh` | list of `{name, geometries}` |
| `/recognition` | build `ocr_predictor(pretrained=True, ...)`, then use its recognition predictor | `reco_arch`, `reco_bs` | list of `{name, value, confidence}` |
| `/ocr` | full `ocr_predictor(pretrained=True, ...)` | detection/recognition architecture and batch fields, orientation/layout/table flags, line/block resolution, threshold fields | list of document pages with orientation, language, dimensions, layout, tables, and OCR blocks/lines/words |
| `/kie` | `kie_predictor(pretrained=True, ...)` | OCR-like fields plus KIE/layout options | list of pages with layout regions and class-named predictions |

The template moves the predictor to `cuda` when `torch.cuda.is_available()` returns true, otherwise to CPU. It also updates the detection model postprocessor thresholds from `bin_thresh` and `box_thresh`.

### Client request pattern

When a service is already running and the user asks how to call it, use multipart uploads and keep the port consistent with how the service was started:

```python
from pathlib import Path
import requests

endpoint = "http://localhost:8080/ocr/"
params = {"det_arch": "db_resnet50", "reco_arch": "crnn_vgg16_bn"}
content = Path("document.jpg").read_bytes()
files = [("files", ("document.jpg", content, "image/jpeg"))]
response = requests.post(endpoint, params=params, files=files, timeout=120)
response.raise_for_status()
print(response.json())
```

Use a trailing slash or a client that follows redirects, because the route handlers are registered at `/.../` under each prefix.

### Production cautions before adapting the template

The template is intentionally minimal. Before treating it as production-ready, make these design choices explicit:

- model lifecycle: the template initializes predictors inside request handling; for sustained traffic, cache or preload approved predictor configurations instead of rebuilding weights on every request;
- downloads: `pretrained=True` and Hub-backed models may download weights on first use, so warm caches deliberately and document offline behavior;
- memory: simultaneous OCR, layout, and table detection can be memory-heavy; bound file sizes, page counts, batch sizes, and concurrent requests;
- security: add authentication, authorization, rate limits, upload size limits, input validation, logging, and monitoring according to the deployment environment;
- errors: return user-safe messages for unsupported MIME types, invalid architecture names, missing optional dependencies, unavailable CUDA, and model download failures;
- ports: keep server startup, Docker port mapping, client examples, and health checks on the same port.

## Streamlit demo shape

The demo is a browser UI for PyTorch OCR exploration. It uses wide layout with four main panes:

1. input page;
2. detection segmentation heatmap;
3. OCR overlay visualization;
4. page reconstitution.

The sidebar lets the user upload `pdf`, `png`, `jpeg`, or `jpg`, choose the page, pick detection/recognition architectures, optionally enable layout and table detection, and tune parameters such as straight-page assumptions, page/crop orientation flags, straightening, straight-box export, binarization threshold, and box threshold.

The demo runtime flow is:

1. read uploaded PDFs with `DocumentFile.from_pdf` or images with `DocumentFile.from_images`;
2. select `cuda:0` when PyTorch reports CUDA availability, else CPU;
3. build an `ocr_predictor` with `pretrained=True` and the selected flags;
4. run the detection model once to display a segmentation heatmap;
5. run full OCR on the selected page;
6. display the page visualization, optional synthesized page, optional extracted tables as dataframes, and the exported JSON.

Local demo dependencies are the package with the `viz` extra, Streamlit, and pandas. Use the demo when the task is interactive model exploration or a user-facing illustration. Do not use it as the default answer for batch automation or service integration.

## Docker guidance

Official docTR container images are published with tag names that encode dependency set, Python version, and either a docTR version or a date-like build marker. Dependency set examples include:

- `torch`: core PyTorch docTR image;
- `torch-viz-html-contrib`: PyTorch image with visualization, HTML, and contrib dependencies.

GPU-ready docTR images are based on CUDA 12.2. For GPU use, the host must have a compatible NVIDIA driver/CUDA stack and Docker must be configured for GPU access. A typical GPU shell command is:

```bash
docker run -it --gpus all ghcr.io/mindee/doctr:torch-py3.9.18-2024-10 bash
```

Choose a current tag that matches the user's Python/docTR needs. After entering a container, verify GPU availability from inside the container before promising acceleration.

For local image builds, the Dockerfile accepts build arguments for framework, Python version, repository owner/name, and docTR version. The default framework is PyTorch. Builds can be slow because Python may be compiled in the image and docTR is installed from the configured Git reference.

The API container pattern uses an application image with FastAPI, Uvicorn, `python-multipart`, and docTR installed, then runs Uvicorn on port 8080 with Docker port mapping to the host. Treat this as a template, not an audited production deployment.
