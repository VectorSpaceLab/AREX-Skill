# CLI development and generated artifacts

Use this reference when changing the CLI or diagnosing drift between source,
help output, generated documentation, and the agent-facing `hf-cli` skill.
The generator/checker scripts in the source repository are maintainer tools;
they are reference-only and are not bundled here because they can rewrite
repository files. Do not invoke an installer or network bootstrap from this
runtime skill.

## Source of truth order

For a released or installed CLI, use this order:

1. `hf <path> --help` from the executable selected by the current environment;
2. the implementation and tests for behavior not visible in help;
3. generated CLI reference documentation for a navigable catalog;
4. prose guide examples for intent and workflow context.

Record the package version and entry-point path when reporting a discrepancy.
The command registry can change between a checkout and an installed wheel; a
reference generated by one version must not silently authorize flags in
another.

Safe source-surface checks:

```bash
HF_HUB_DISABLE_UPDATE_CHECK=1 hf --help
HF_HUB_DISABLE_UPDATE_CHECK=1 hf download --help
HF_HUB_DISABLE_UPDATE_CHECK=1 hf skills --help
```

The help checker bundled with this skill performs bounded read-only variants
of these probes. Its parser accepts only a trusted executable named `hf`, at
most 32 custom command paths, at most eight command-name tokens per path, and
a finite per-probe timeout in `(0, 60]` seconds. Probe count multiplied by the
per-probe timeout cannot exceed 300 seconds. Command tokens must use the
exact built-in command-path allowlist and the conservative
`[A-Za-z0-9._-]` grammar. Positional arguments—including an extension name
after `extensions exec`—option-like values, shell syntax, paths as probes, and
extra executable names are rejected. This matters because pass-through leaves
can forward tokens after a positional name. The checker appends `--help`, uses
no shell, captures streams separately,
always disables startup update checks, and returns non-zero if any probe
fails or times out. On POSIX it starts each probe in a new session and kills
that process group on timeout, preventing a child from retaining the captured
pipes. It does not run `make style`, install dependencies, invoke network
installers, or write generated docs.

Examples:

```bash
python scripts/check_cli_help.py --timeout 10
python scripts/check_cli_help.py --probe 'jobs wait' --probe 'sandbox kill'
```

The checker offers no override for startup update checks: enabling them could
introduce network access, advisory stderr, or local freshness timestamps, which
would violate the helper's deterministic read-only contract.

## Generated CLI reference

The package's CLI-reference generator derives documentation from the
registered commands. When changing a command's name, alias, help, parameter,
or example, maintainers should regenerate the reference and run its focused
tests. Do not hand-edit the generated package-reference page as a durable fix;
hand edits will be overwritten.

Check that:

- aliases are represented once with the primary command name;
- argument vs option sections match live help;
- choices, defaults, repeatable options, and deprecation notes are current;
- global formatting options appear for modern leaves but not pass-through
  extension execution;
- examples are safe, current, and do not expose real credentials or imply an
  unapproved mutation.

## Static imports and `__all__`

Public API changes can require the repository's static import and `__all__`
checks. The maintainer static-import and export checkers are source-side
validation tools. Use the project quality workflow after reviewing their
proposed changes; do not copy them into this skill or link future users to a
checkout path.

The normal maintainer sequence is:

```bash
# MAINTAINER MUTATION: formats code and may update generated files.
make style
# MAINTAINER CHECK: validates style, generated surfaces, lint, and types.
make quality
```

Run this only in a controlled development checkout after reviewing the diff.
A user asking how to use `hf` does not need this workflow. A generated-doc
failure should be diagnosed as drift first, not fixed by suppressing a check.

## Command implementation checklist

For a new or changed command:

1. Choose a resource/action route and a clear safety classification.
2. Declare parameters through the repository's framework markers and preserve
   explicit `--type/--repo-type`, `--revision`, token, and output conventions.
3. Add aliases only when the alternate spelling is intentional; pipe-separated
   declarations are surfaced in help.
4. Send structured data through the output sink. Keep warnings, errors, hints,
   and progress on stderr.
5. Gate destructive operations with the confirmation helper and expose
   `-y/--yes` only when a non-interactive bypass is justified.
6. Add focused tests for help, JSON/quiet/agent behavior, error status, URI
   validation, and confirmation refusal.
7. Regenerate CLI documentation and run static quality checks.
8. Add a subprocess-level test when stdout/stderr or a pass-through boundary is
   part of the contract.

## Generated `hf-cli` skill versus this skill

The default marketplace skill ID `hf-cli` is generated at runtime by
`hf skills preview` from the installed command registry. `hf skills add`
installs it into a project/global agent skills root, and `hf skills update`
refreshes managed installs. Those files are target-side artifacts. They are
not source files for this sub-skill, and they must not be used to overwrite
`skills/huggingface-hub/sub-skills/cli-and-automation/`.

The startup freshness checker is advisory and local: it compares the generated
version stamp at most daily and prints a hint. It does not install/update the
skill. There is no explicit `hf skills check` command in the checked source;
use `hf skills --help`, inspect target-side files safely, or deliberately run
`hf skills update` when a refresh is approved.
